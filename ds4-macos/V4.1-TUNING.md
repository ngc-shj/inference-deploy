# Tuning DeepSeek V4.1 Flash decode on Apple Silicon

Working notes from optimizing [ds4 (DwarfStar)](https://github.com/antirez/ds4)'s
Metal decode path for DeepSeek-V4.1-Flash Q2, on the branch
`perf/v41-metal-apple` in [ngc-shj/ds4](https://github.com/ngc-shj/ds4).

Box: **MacBook Pro, Apple M5 Max, 128 GB** unified memory, macOS 26.6.2.
Model: `DeepSeek-V4.1-Flash-Q2.gguf`, 340.6 GiB (152 GiB of weights plus 189 GiB
of Engram tables that stay on disk), served with `--ssd-streaming --ctx 32768`.

> Correction: commits `722aee8` and `40f5934` on that branch say the numbers were
> measured on an M3 Ultra. They were not — every number here and there comes from
> the M5 Max above. The commit messages could not be rewritten (the history had
> already been shared), so the correction lives here.

Single-stream decode over this work: **12.17 → 18.11 tok/s**, every step gated on
byte-identical output against the arm it was compared with. The last figure was
taken on a machine that had been hot for hours; the same build measured 19.8 on
a cool one earlier in the day.

The largest single win came last and from the least expected place. The gap
between one layer's command buffer and the next is 0.558 ms, and this document
spent most of its length treating that as the cost of the readback. The readback
is 0.15 ms of it. **The other 0.40 ms is the host**, and most of that turned out
to be two waits it did not need:

| | before | after |
|---|---|---|
| `missing_bind` per split layer | 0.355 ms | 0.033 ms |
| `missing_wait` per split layer | 0.291 ms | 0.000 ms |
| host work per layer | 0.402 ms | 0.233 ms |
| throughput (hot machine) | 15.35 tok/s | 18.11 tok/s |

The first wait was for a cache slot: the cache is indexed by expert, so
installing an expert whose slot the GPU is still reading drained every command
buffer in flight. Under zero-copy there is nothing to wait for — the buffers are
already mapped and only the bookkeeping wants that slot — so the entry goes into
one of eight spares per layer instead (`559e89a`, +4.4%).

The second was worse: after submitting the cached experts, the host waited for
that command buffer to *complete* before encoding the pass for the ones it had
to fetch. Command buffers on one queue run in the order they were committed, so
the missing pass could never have overtaken the resident one. The wait bought
nothing (`5888313`, +18%).

## The finding that ties the rest together: host round trips per token

Same kernel, same data, same total work — only the packaging differs
(`iq2bench`, the expert matvec on its own, 40 dispatches of a 1536×5120 IQ2_XXS
gate/up pair):

| how the 40 dispatches are issued | GPU time | effective |
|---|---|---|
| one command buffer, back to back | 0.79 ms | 205.8 GB/s |
| 40 command buffers, no host gap | 6.44 ms | 25.2 GB/s |
| 40 command buffers, 100 us gap | 7.18 ms | 22.6 GB/s |
| 40 command buffers, 300 us gap | 9.95 ms | 16.3 GB/s |
| 40 command buffers, 600 us gap | 13.82 ms | 11.7 GB/s |

**Splitting the work into one command buffer per dispatch costs 8x before a
single microsecond of host gap is added**, and the 600 us gap a decode actually
has takes it to 17x. The host sleeps are subtracted from these times, so this is
GPU-side cost only.

It is not the packaging, though. Two controls settle what it is:

| | GPU time | effective |
|---|---|---|
| one buffer, a barrier between every dispatch (no concurrency) | 0.79 ms | 204.5 GB/s |
| one buffer, the host signalled between every dispatch (`encodeSignalEvent` + `encodeWaitForEvent`) | 6.69 ms | 24.2 GB/s |
| 40 buffers, host round trip between every dispatch | 6.73 ms | 24.1 GB/s |

Serialising the dispatches inside one buffer costs nothing. Stopping for the
host costs the same whether the work is in one command buffer or forty. So the
unit of cost is **the round trip to the host — about 0.15 ms of GPU time each**
— and `encodeWaitForEvent`, which the header calls a pause rather than a
resubmission, does not avoid it.

ds4 makes about **40 of those round trips per token**, one per layer, because
only the host can page in an expert the router picked that is not cached. That
one fact accounts for both halves of the decode: the 28 ms the GPU spends idle
*and* the 136 GB/s it manages while running, which is what this same kernel does
at that duty cycle. It is not the kernel's instruction mix, not memory
bandwidth, and not the power state.

It also explains the failures above. The speculative resident pass and moving
the shared expert after the signal both kept the round trips exactly as they
were, so neither could have helped.

### Why the round trip is there, and what unified memory does and does not buy

An expert-sized (9.49 MiB) no-copy view over a cold part of the file, measured
against the same view once its pages have been touched:

| | cost |
|---|---|
| creating the view | 0.02–0.04 ms |
| first GPU read of it (pages not yet GPU-resident) | 1.0–4.8 ms |
| reading it again | 0.20–0.91 ms |
| a **new** view over the same, already-resident pages | 0.28–0.80 ms |

Two things follow. First, a fresh view over pages that are already resident
costs the same as re-reading the old one, so ds4 making a new view per miss is
not the waste it looks like — the expense is the one-time residency, not the
view. Second, that first read moves 9.49 MiB in 1.7 ms, which is 5.5 GB/s on
memory that does 600 GB/s: **99% of it is page bookkeeping, about 0.7 us per
4 KiB page, not data movement.** Unified memory removed the copy — ds4 reads
weights in place at full bandwidth — and left the mapping cost behind.

### Why the round trip cannot simply be dropped

Three measurements settle it.

**The data is already in memory.** `mincore` over every missed expert during a
384-token generation: **100% of their pages were already resident**, across
47,400 misses. A cache miss in ds4 means the expert is not in *its* address
table, not that anything has to come off the SSD. The round trip is
bookkeeping, not I/O.

**Making everything addressable is free.** One `mmap` of the whole 340.6 GiB
file takes 450 ms, and carving **15,360 no-copy buffers out of it takes 43 ms —
2.8 us each**, with the process footprint unchanged (0.12 GiB at 256 buffers,
51 GiB still free). A full expert address table could be built at startup. The
earlier attempt at one measured 0.04 tok/s, but creating the buffers is not what
costs.

**What costs is that the pages cannot be given back.** A buffer's pages are
wired when the GPU first touches it, and `setPurgeableState:` — the one API for
handing memory back — is ignored for no-copy buffers:

| buffer | set Volatile | state afterwards |
|---|---|---|
| allocated by Metal | previous: NonVolatile | **Volatile** |
| `newBufferWithBytesNoCopy` | previous: NonVolatile | **NonVolatile** |

So addressability and a bounded resident set cannot both be had. Bounding the
resident set means releasing buffers; releasing them invalidates addresses; and
the GPU cannot know which addresses went stale. Somebody has to tell it, once
per layer, and that somebody is the host.

ds4's expert cache plus its per-layer readback is what that constraint forces.
The 6 ms/token of round trips is not waste to be removed — it is the price of
running a 152 GiB expert set through 128 GB of memory.

That conclusion stands, but it was the wrong thing to have been optimising:
the readback is 6 ms of a 52 ms token, and the host's own work around it was
16 ms. Removing two waits from that window was worth more than every attempt at
the readback put together.

The expert cache hit rate is **0.850** (88,385 hits against 15,646 misses over a
384-token generation, 7,498 of the model's 15,360 experts resident). A layer
needs six lookups, so only 0.85^6 = **38%** of layers are clean — merging layers
optimistically and redoing the ones that miss would redo almost everything.

## The ceiling this is working towards

Per token the decode must read 6 experts × 9.49 MiB × 40 layers = **2.28 GiB** of
expert weights. The IQ2_XXS matvec measures 387 GB/s standalone at large sizes —
dequantisation is the limit, not the 600 GB/s the memory does — so:

```
floor, if nothing were wasted    2.28 GiB / 387 GB/s = 5.9 ms/token = 170 tok/s
now                              52 ms/token = 19 tok/s
  of which the GPU is idle       28 ms   (all of it between command buffers)
  of which the GPU is running    24 ms   (2.28 GiB at ~136 GB/s effective)
```

Both halves are roughly equally far off. Removing every idle gap alone caps out
near 2x; the running half is 4x off its own standalone ceiling. Neither is
enough on its own.

## Where a decode token goes

Measured with `DS4_V41_DECODE_PROFILE=1` and an Instruments Metal System Trace
(`metal-gpu-intervals`), on the shipping configuration, warm cache:

| | ms/token |
|---|---|
| MoE | ~46 |
| pre-MoE | 1.7 |
| logits | 1.3 |
| engram | 0.7 |
| everything else | 1.0 |
| **total** | **~52** |

The GPU is busy for **46%** of that. The other 54% — about 28 ms per token — is
idle, and all of it sits **between command buffers**:

```
command buffers            ~39 per token (one per layer)
gaps inside a command buffer   none (busy ratio 1.00)
gaps between command buffers   6928 ms of the 6963 ms of idle
CPU->GPU submission latency    median 564 us, p90 1248 us
kernel duration                median 181 us
```

A layer's work is submitted, and the GPU takes longer to *start* it than to *run*
it. What the submission latency is spent on has not been established. The
per-layer command buffer comes from the router: the kernel picks six experts,
and the host has to learn which, because only the host can bring an uncached
expert in from the file.

A CPU profile of the decode thread says the same thing from the other side —
of 9772 samples, 7666 are blocked in `waitUntilSignaledValue`. Encoding costs
about 30 samples. **The host is not encoding, it is waiting.**

## What the submission latency is made of

It is not a fixed cost. Keeping the GPU busy halves it:

| | GPU busy | submission latency (median) | gap between command buffers |
|---|---|---|---|
| baseline | 46.4% | 564 us | 558 us |
| with the pacer | 43.9% | 283 us | 248 us |

So the latency is not a fixed cost, and something about keeping the queue busy
halves it. *Why* is not established, and the obvious explanation is now ruled
out: on the current build the GPU already spends most of a decode at its top
performance state, and the pacer barely moves it.

| performance state | without the pacer | with the pacer |
|---|---|---|
| Maximum | 64.8% | 69.0% |
| Medium | 17.9% | 14.7% |
| Minimum | 17.2% | 16.3% |

An earlier trace of this decode — before the queue gating, zero-copy reads and
BF16 fusion — had it at the **minimum** state 58.7% of the time, and that figure
was quoted for a while after it stopped being true. Four points of extra
Maximum residency does not explain +10% throughput and a halved submission
latency; what does is not known.

## What worked

| change | effect |
|---|---|
| Read streamed experts where they lie (`DS4_METAL_ZERO_COPY_EXPERTS`) | no copy into slabs; mmap views read at 599.8 GB/s |
| Round the HC weighted sum to BF16 in the kernel that produces it | drops a whole pass at three sites |
| Batch sessions through one readback | 4 sessions: 19.67 tok/s aggregate |
| Parallel Engram reads from 2 rows up (was 256) | decode reads 48 rows, never 256 |
| **GPU pacer** (`DS4_METAL_GPU_PACER=1`) | **+10%**: 17.99/17.62 → 19.84 tok/s |
| **Spare cache entries instead of draining for a slot** | **+4.4%**: 14.71 → 15.35 tok/s |
| **Dropping the host wait for the resident pass** | **+18%**: 15.35 → 18.11 tok/s |
| **Committing the expert dispatches instead of holding them** | **+5.9%**: 52.95 → 50.01 ms/token |

The pacer runs throwaway ALU work on a second queue while the main queue is
busy, and stops on its own after 20 ms of quiet. It is worth tuning, not
scaling: 16 threadgroups x 2000 iterations gives +10%, 64 x 2000 gives nothing,
and 16 x 8000 costs 28%. Which property of the pacing does the work — the rate
of submissions, the occupancy, something else — is not established; only the
shape of the curve is measured.

The last two are described at the top. Both were found by timing the window
between the readback returning and the layer's work being submitted
(`DS4_METAL_HOST_LAYER_MS`), which nothing had measured before: it was 0.5 ms a
layer, 20 ms a token, larger than anything else on the table.

## What did not work

- **Speculating the resident experts before the readback.** The masked
  address-table kernel reads the real ids and skips uncached lanes, so the pass
  is correct whatever the router chose. It still measured 17.86/17.82 against
  18.48/18.27 tok/s. Same command buffer count, no duplicated work, output
  identical — where the 3 ms/token goes is not established. Reverted (`722aee8`).
- **An `MTLResidencySet` for the expert slabs instead of naming them per
  dispatch.** No measurable change.
- **Spinning on the shared event** instead of sleeping: 54.5 → 59.4 ms/token.
- **A full expert address table** (all 384 experts per layer addressable):
  0.04 tok/s. See the next section for what that actually costs.
- **Moving the shared expert after the selected-id signal**, so the GPU has
  id-independent work to run while the host wakes: 15.03/14.58 against
  15.85/15.22 tok/s. The traced arm issued about 16% more command buffers per
  token than the baseline arm; whether that is what cost the throughput is not
  established. Reverted.

## A no-copy window over the file is an eager load, not a lazy map

`newBufferWithBytesNoCopy` over a range of the mmapped GGUF returns in about a
millisecond, but the **first GPU access to it pulls the whole range in**:

| window | first access | implied rate |
|---|---|---|
| 4 GiB | 695 ms | 5.8 GB/s |
| 16 GiB | 2667 ms | 6.0 GB/s |
| 40 GiB | 11244 ms | 3.6 GB/s |
| 64 GiB | 16105 ms | 4.0 GB/s |

Linear in the window, at this SSD's read speed. Afterwards every read of that
window costs the same whether or not the host ever touched the pages
(0.20–0.32 ms for a 9.49 MiB expert either way).

This kills the design where the kernel addresses any expert arithmetically out
of two or three large windows and the per-layer readback disappears: the
windows would have to cover 152 GiB of experts on a 128 GB box, and creating
them means reading all of it. It is also why the full address table measured
0.04 tok/s — the cost was the mapping, not per-page faults. ds4's shape — a
small no-copy view per expert, with the host issuing readahead first — is the
one that fits this behaviour: each view wires 9.49 MiB, and the host has
usually already pulled those pages.

The consequence for the idle time: the per-layer readback is structural. Only
the host can make an expert's pages resident, and it cannot know which expert
without the router's ids.

### Remapping the pages under a live buffer does not reach the GPU

The way around an eager window would be a small fixed window whose pages are
swapped for whichever experts are wanted — bank switching. `mmap(MAP_FIXED)`
over the range a no-copy `MTLBuffer` already wraps does not do it:

| | host sees | the existing buffer's kernel sees | a buffer created after the remap |
|---|---|---|---|
| bank at 60 GiB | `c9adfa79` | `c9adfa79` | `c9adfa79` |
| remapped to 90 GiB | `92c269de` | `c9adfa79` | `92c269de` |
| remapped to 120 GiB | `c2d10376` | `c9adfa79` | `c2d10376` |

The buffer keeps what it was created over. Nothing fails — no error, no crash,
just the old bytes, which makes this a silent-corruption trap rather than an
unsupported call.

What the documentation actually says is nothing: the SDK header describes
`newBufferWithBytesNoCopy:` only as "create a buffer by wrapping an existing
part of the address space", and says nothing about changing the mapping
underneath. `didModifyRange:` is for managed storage and does not apply on
Apple Silicon. So this is measured behaviour of this OS and driver, not a
documented contract.

Metal's own mechanism for this is **placement sparse** (macOS 26 / Metal 4:
`updateSparseBufferMappings`, `MTL4UpdateSparseBufferMappingOperation`,
`placementSparsePageSize`), which remaps a sparse resource's pages onto heap
memory. Heap memory, not file pages — so using it means copying experts from
the file into a heap, which is the slab design again, with stable addresses.
Not tried.

**Indirect command buffers** are not tried either, and on this evidence not
worth trying: an ICB removes host-side encoding, and host-side encoding is 0.3%
of the decode thread. The hardware supports them (compute ICBs and their memory
barriers need Apple3, residency sets Apple6, and the ICB length is unlimited),
so the option stays open if the balance ever shifts.

## Three ways to remove the readback, and why each loses

The readback exists to rewrite an address table. That is a fact about the
current design, not a law, so all three alternatives were built and measured.

**A full address table** — every expert addressable, so nothing to rewrite.
Works, output byte-identical, round trips drop exactly as intended (40 → 32 per
token at 8 layers, counted). Slower at every size: 12.22 tok/s at 4 layers,
11.42 at 8, 8.99 at 19, against ~15-18. Two costs. The layer can no longer use
the deferred split, so it computes all six experts in one pass instead of
starting the cached ones while the host fetches the rest. And every buffer it
can reach must be declared resident: dropping the residency set makes it 15%
faster (11.89 → 13.71 tok/s) **and changes the output**, because the kernel
then dereferences addresses whose pages the GPU was never given. Reads only,
of our own mapping, so nothing is corrupted outside the answer — but it is a
silent wrong answer, so that combination now aborts instead.

**Placement sparse** (macOS 26) — permanent addresses, physical pages mapped
only where wanted, one resource instead of 46,080. Everything about it works on
this machine:

| | cost |
|---|---|
| 152 GiB placement sparse buffer over the whole expert set | 1.1 ms |
| placement heap | 0.3 ms |
| mapping one expert's 38 tiles (256 KiB each) | 0.003–0.05 ms |
| filling one expert by GPU blit from the file mapping | 0.455–1.155 ms |

The mapping update is an order of magnitude below the 0.15 ms round trip it
would replace. What it cannot avoid is a copy: a sparse buffer's pages come
from a heap, and a heap cannot be made out of pages that already exist, so the
file bytes have to be moved. Against **0.03 ms** to wrap those same bytes in a
no-copy view, filling by blit is fifteen times worse, on roughly 36 misses a
token.

The storage modes are worth writing down, because the first attempt guessed
them wrong: the sparse **buffer** must be Private (Shared asserts with "Invalid
Storage Mode 0 for Placement Sparse Buffer"), but the **heap** backing it may
be Shared, and a buffer placed in a shared heap hands back a CPU pointer the
host can write through. So the fill does not have to be a GPU blit. It does not
help:

| filling one expert into sparse heap memory | cost | rate |
|---|---|---|
| GPU blit from the file mapping | 0.455–1.155 ms | 9–22 GB/s |
| host `memcpy` from the file mapping | 0.551–0.646 ms | 15–18 GB/s |
| host `pread` straight from the file | 0.771–3.646 ms | 3–13 GB/s |
| **what ds4 does instead: wrap the bytes in a view** | **0.03 ms** | — |

Writing 9.49 MiB at 16 GB/s on memory that reads at 600 is the same story as
the 0.7 us per page above: the destination pages are new, so the cost is
faulting and accounting for them, not moving bytes. At roughly 36 misses a
token that is 20 ms/token to save 6 ms of round trips.

So placement sparse works in every respect — permanent addresses, one resource,
mapping updates an order of magnitude cheaper than the round trip — and still
loses, because it has to move the data at all. That is the line every
alternative crosses and ds4 does not.

**Bank switching** with `mmap(MAP_FIXED)` under a live buffer — covered above:
the GPU keeps the pages the buffer was created over, silently.

What the three have in common is that the round trip is the cheapest way found
to avoid moving data. Unified memory's gift is that the file pages *are* the
memory; every design that gives that up pays more than the 0.15 ms it saves.

## Speculative decoding: three assumptions, two of them wrong

The plan was to get more tokens out of one pass over the weights. Verify k
drafted tokens as k rows of one batch, and an expert's 2.28 GiB a token is read
once for all of them instead of once each. That rests on three things, none of
which was safe to assume: that the batch path takes consecutive positions of one
session, that a rolled-back session reproduces its own output, and that k rows
cost less than k single steps. All three are now measured. The first is true,
the second was false for a reason worth knowing, and the third is true but by
far too little.

`ds41_graph_step_batch` does take consecutive positions of one session: that is
what `prefill_rows` already means, and `ds41_graph_short_prefill` already calls
it that way. Two things stood in the way of using it as a verifier. `prefill_only`
conflated "consecutive positions" with "publish only the frontier row", so a
verifier could never see the k sets of logits it exists to compare. And under
streaming the batch skipped `ds41_moe_batch` and ran the rows through the
single-row expert path one at a time — the opposite of sharing.

### The rows do not share the weight read, and the address table does not change that

Metal already holds a batched streaming expert path whose conditions match V4.1
Flash exactly — `n_expert == 6`, gate `IQ2_XXS`, down `Q2_K`, 2 to 800 rows —
and it had never run on this model. `ds41_moe_batch` passes
`force_resident = true`, which is right for a large prefill's sequential
whole-layer read and wrong for a batch of four, and nothing else asked for it.
Wiring it up (`DS4_METAL_V41_BATCH_STREAM_EXPERTS`) is correct: output bytes
identical across four concurrent sessions, and identical argmax over 192
verified rows.

It is also worth very little.

| k | per-row experts | address table | |
|---|---|---|---|
| 4 | 159.10 ms/step | 152.89 ms/step | −3.9% |
| 8 | 299.25 ms/step | 279.73 ms/step | −6.5% |

The table stages the union of the rows' selections — 15.8 unique experts of 24
at k=4, 24.6 of 48 at k=8 — so a third of the *staging* disappears. A third of
the *read* does not, and that is the whole story: `v41_decode_batch` in
`ds4_metal.m` pins V4.1 to the per-row `mul_mv` kernels for any batch of eight
or fewer, and its comment says why — the grouped matmul changes the reduction
order before V4.1's BF16 and router boundaries. Each row therefore re-reads its
own six experts whatever the table staged, and 34% fewer unique experts buys 6%.

The dispatch says it plainly: `pairs = nei0 * nei1` is six slices per row, and
the kernel recovers `(row, slot)` from `tgpig.z`, resolves that slot's expert
address and calls the single-row matvec. Two rows that chose the same expert
stream its weights twice. What the address table removes is the buffer and
address preparation for the duplicates, which is all the 4-6% ever was.

Consecutive positions of one session barely route more alike than four
independent sessions answering the same prompt: 15.8 unique selections of 24
against 16.3 of 23.9. There is no same-context bonus worth collecting.

### What a batched row costs

Medians of three alternating rounds inside one process, so that the machine's
±10% between runs cannot decide the answer. Single-step reference in the same
rounds.

| k | single | k-row step | ratio | marginal row | break-even |
|---|---|---|---|---|---|
| 4 | 50.40 ms | 152.89 ms | 3.03x | 34.16 ms (68%) | accept 76% |
| 8 | 51.63 ms | 272.96 ms | 5.29x | 31.62 ms (61%) | accept 66% |

A row inside a batch costs 61% of a standalone token. Batching amortises the
fixed part of a step — about 30 ms, which is the same order as the 28 ms of
command-buffer idle measured above — and nothing else. Break-even is
`0.61 + 0.39/k` of the drafted tokens, so **no drafting depth brings the
requirement below about 61% acceptance**. Prompt-lookup drafting on generated
code does not reach that, and gating on long n-gram matches only lowers the hit
rate, which dilutes the effect without moving break-even.

Where the marginal row goes, from command-buffer boundaries around each stage
(the totals run high, the shares are the point):

| stage | per extra row | share |
|---|---|---|
| routed + shared MoE | 39.2 ms | 61% |
| per-row attention | 16.5 ms | 26% |
| batched HC / Engram / attention projection | 8.1 ms | 13% |

So the 61% is where the 61% is. Making the expert matvec tile over rows — one
weight load feeding every row that selected that expert — is the only change
with enough room in it to make speculation pay. It is also the change the
current kernel choice deliberately refuses, and the refusal buys the exact
agreement between batch and single rows that every measurement here relies on.

### Row-tiled IQ2: the kernel does pay, and it stays bit-identical

Sharing the weight decode across token rows keeps the result exact, which is
the constraint `v41_decode_batch` is protecting. Each row still adds its terms
in the same ib32/l/j order, and the sign is exactly +/-1.0, so moving it from
`(v*g)*s` to `v*(g*s)` changes nothing. Measured against the kernel the engine
dispatches today, one expert's gate/up matvec, arms alternating:

| tile | today (T x single-row) | tiled | saved | marginal row |
|---|---|---|---|---|
| 2 rows | 0.040 ms | 0.032 ms | 20% | 64% |
| 3 rows | 0.059 ms | 0.042 ms | 29% | 57% |
| 4 rows | 0.079 ms | 0.053 ms | 33% | 57% |

Outputs compare identical at every width.

The layout decides whether this works at all. Holding `yl[TROWS][32]` live
across the output-channel loop spills past two rows and collapses — a 3-row
tile costs 4.06 single-row dispatches, a 4-row tile 8.57. Keeping only the
eight activations the current `l` needs costs a re-read of y per output channel
— 20 KiB a row, cached — and removes the spill entirely.

What this is *not*: a memory win. The untiled arm runs at 307 GB/s here, above
the 205 GB/s this document quotes elsewhere, and cycling a 371 MiB pool of
experts to defeat the cache does not move it. The kernel is bound by the
dequantisation, not the read, so what tiling amortises is the grid lookup and
sign work. That also means the saving is capped by how often two rows pick the
same expert, which is 24.6 unique of 48 selections at k=8: pairing every
duplicate is worth about a quarter of the gate/up time, not a half.

### How much of that the routing will actually give up

The mean of 1.95 rows an expert is the wrong statistic, because only a second
row on the *same* expert saves anything. Modelling a greedy widest-first
pairing against the measured tile costs, over 600 live layers at k=8:

| rows choosing one expert | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
|---|---|---|---|---|---|---|---|---|
| experts, mean per layer | 14.58 | 4.57 | 2.13 | 1.19 | 0.84 | 0.59 | 0.38 | 0.34 |

Fourteen and a half of the 24.6 unique experts are chosen by exactly one row,
and no tile can help them. Width-2 tiling takes the gate/up time to 88.7% of
what it is now; width-4, with three more kernel variants to write, takes it to
81.7%.

Through the stage split — MoE 61% of the marginal row, gate/up the larger part
of it — that is about 6% off the marginal row, which moves break-even from 65%
acceptance to 61%. Four points, for a host-side grouping pass, a tile
descriptor buffer, a dispatch restructuring and three kernel variants. **Not
the lever.** It remains a ~6% throughput gain for concurrent serving at k=8,
where there is no acceptance rate to bet on, and that is the case for building
it if it is ever built.

### There is no in-situ bandwidth gap to go after

It looked like there was. Dividing the coarse MoE stage by the expert bytes
gives about 132 GB/s against the kernel's 307 GB/s standalone, which would have
been the largest number on the table. The in-situ profile says otherwise:
`DS4_METAL_MOE_STAGE_PROFILE` at k=8 reports gate/up at 1.198 ms for 48 pairs
of 6.08 MiB, which is **244 GB/s**, and down at 0.749 ms for 3.87 MiB a pair,
which is 248 GB/s. The kernels keep four fifths of their standalone rate inside
the decode loop. The 132 GB/s was a coarse stage divided by the wrong bytes.

Three things that could have explained a gap were measured and do not:

| | cost |
|---|---|
| address table and `reinterpret_cast` instead of a bound buffer | +3.3% |
| no-copy views scattered over the 340 GiB mapping instead of a compact pool | −0.2% |
| bursts of 6 with a host round trip between them instead of continuous | +3% |

`DS4_METAL_ZERO_COPY_EXPERTS` is vindicated by the second of those: where the
bytes lie costs nothing once the pages are resident.

Splitting the MoE further (`DS4_V41_MOE_SPLIT_MS`, k=8, per layer): router
0.34 ms, shared expert 0.42 ms, routed experts 2.3 ms. The shared expert is the
same 37 MiB for every row and the Q8_0 matvec does dispatch a slice per row,
but at 8 rows that re-read is served from cache and costs 2.1 ms a row — 7% of
the marginal, not the fifth it looks like on paper.

So the marginal row divides roughly as routed experts 37%, per-row attention
26%, the batched pre-attention work 13%, shared expert 7%, router 6%. Nothing
in it is a single large lever, which is the answer to whether speculative
decoding can be made to pay here: not by one change.

### A rolled-back session does not reproduce itself unless the pair carry comes back

Rewinding `pos` and the Engram history is not enough. Re-decoding 64 positions
from 49 gave a different token at offset 44 every time — where the reference had
led second place by 0.447, so not a flipped near-tie — and successive rewound
passes did not even agree with each other. It happens with the batch path
removed entirely, so it is the rewind, not the batch.

`ds41_attention_publish` pools two positions into one compressed entry on the
`ratio == 2` layers, and carries the first half in `previous_kv[owner]` and
`previous_score[owner]`. Those are carried step to step rather than indexed by
position, so `pos` alone does not describe them. `ds41_state_spans` already says
this — it saves them, for owners 0..2, exactly when `pos` is odd — but only the
session save path knew it. Rewinding to position 49 left the carry from position
112 in place, poisoning one compressed entry, which changed nothing until
attention first selected it.

Restoring those six tensors on rewind makes it exact: rollback reproduces its
own output, and the batch agrees with single steps on all 192 rows at k=8. Any
speculative implementation needs this, and without it the failure is silent.

## The host's work between layers is mostly not in the way

`DS4_METAL_HOST_LAYER_MS` still reports 0.218 ms a layer, one selected-id round
trip a layer, against a 52 ms token: 8.7 ms, 17% of the token, and the largest
single item left for one stream. A `sample` of the decode thread agrees on the
size — 9776 samples, 8032 of them parked in `waitUntilSignaledValue`, 1744
(17.8%) doing host work — and says what the host work is:

| | samples | share of host work |
|---|---|---|
| `fcntl(F_RDADVISE)` expert readahead | 211 | 12% |
| `newBufferWithBytesNoCopy` (a `mach_msg` each) | 42 | 2% |
| reusable-cache-entry scan | 16 | 1% |
| the rest: encoding outside the streaming cache | ~1475 | 85% |

The readahead looked like the thing to remove. It is real — 18,768 `F_RDADVISE`
calls and 58 GiB advised in one short run, on pages `mincore` already calls
resident — and it is the largest named piece of the host's work. Removing it
changes nothing: an in-process A/B on
`DS4_METAL_DISABLE_STREAMING_EXPERT_READAHEAD`, five alternating rounds,
measures **+0.2%** with every round between 51.5 and 53.0 ms.

So that part of the host work runs while the GPU is busy and never gates
anything. That does not settle the other 85% — removing a host wait was worth
+18% not long ago, so some of what happens between layers is on the critical
path — but it does say the 8.7 ms is not 8.7 ms of recoverable time, and that
the way to find the part that is, is to remove candidates and measure rather
than to add up a profile.

### Alternating both arms inside one process

`DS4_V41_VERIFY_SELFTEST_AB=<VARIABLE>` runs the single-step arms with that
variable set and unset, round by round, against one set of weights in the same
minute. It settled the readahead question in one run of about a minute, where
an arm-per-server comparison could not have resolved 2%.

It only works for a variable the code reads on every use. `DS4_METAL_GPU_PACER`
is read once, during GPU init: toggling it from here starts nothing, both arms
are identical, and the harness reports a confident 0.6% that means nothing at
all. That number was believed for several minutes. The guard is the one already
written down here — make the change announce itself, and check the announcement
before reading the timing.

### What settled the pacer, after two things that did not

The pacer's +10% above was measured hot, with a server per arm. Re-measuring it
took three attempts and the first two produced numbers that looked like answers.

Starting a server per arm, two passes each, alternating: **54.44 and 53.98 ms a
token without, 48.76 and 56.60 with**. The two pacer runs disagree by 16%. That
is the between-run drift this file keeps warning about, and no amount of
within-run rounds fixes it, because the medians inside each run were tight.

The in-process harness could not toggle it. `ds4_gpu_pacer_start` is called once
during GPU init, so setting `DS4_METAL_GPU_PACER` from inside a running process
starts nothing: both arms ran without a pacer, and the harness reported +0.6%
with a straight face. What caught it was the rule already written down here —
the change announces itself, and `grep` for the announcement found zero
occurrences of `GPU pacer on` in a log that should have had one.

`DS4_METAL_GPU_PACER_DYNAMIC` makes the pacer follow the variable while the
process runs, and announce each start and stop. Seven alternating rounds, with
seven starts and seven stops in the log:

| | unset | set |
|---|---|---|
| median | 62.79 ms/token | **59.63 ms/token** |
| rounds where the pacer won | | 7 of 7 |

**-5.0%**, and unanimous. The absolute numbers are a hot machine — 62 ms a token
against 51 cooled — so the magnitude on a cool one is still open, but the sign
and rough size are not.

## Nothing was submitted while the host encoded the next layer

Splitting the 0.229 ms the host spends between one selected-id wait and the
next — marking it directly rather than adding up a profile — gives three parts
that sum to the whole:

| | ms/layer | of the token |
|---|---|---|
| bind and encode the experts the readback named | 0.080 | 3.2 ms |
| **everything the graph does between routed calls** | **0.147** | **5.9 ms** |
| the next layer's router and shared expert encode | 0.002 | 0.1 ms |

The middle one is the next layer's attention being encoded. Nothing is
submitted while that happens: the expert dispatches the readback just named sit
in an open command buffer until the *next* layer's wait commits it, so the GPU
has nothing to run for 5.9 ms of a 53 ms token.

The queue already orders whatever is encoded after a commit — the property that
paid for `5888313` — so committing once the expert dispatches are encoded costs
a command buffer boundary and lets the GPU start the experts while the host
encodes the attention that follows them. Seven alternating in-process rounds,
every one of them favouring it:

| | median |
|---|---|
| holding the dispatches | 52.95 ms/token |
| `DS4_METAL_V41_EARLY_COMMIT=1` | **50.01 ms/token** |

**−5.6%**, and the two arms do not overlap at all: 52.51–53.45 against
49.74–50.34. The greedy choice matches the reference at all 448 positions
checked, and a 256-token generation compares byte-identical against the arm
without it.

It also survives the pacer, which attacks the same idle from the other side:
with `DS4_METAL_GPU_PACER=1` in both arms, the early commit is still worth
**−4.2%**, five rounds out of five. Less than −5.6%, as two changes competing
for the same gap should be.

## How to measure this without fooling yourself

1. **Discard a warm-up request in every arm.** The first request after a build
   runs ~23% slower than the steady state (63.73 vs 51.68 ms/token for identical
   code) because both the expert cache and the page cache start cold. An A/B
   whose arms each start a fresh server and measure their first request is
   measuring its own run order. Two of the conclusions above were wrong the
   first time for exactly this reason.
2. **Prove the code path ran.** Print a one-shot note from inside the change.
   `DS4_METAL_ZERO_COPY_EXPERTS` leaves the slab count at zero, which silently
   disabled a slab-gated path in *both* arms of an A/B that then looked like a
   22% win — it was the run-order bias, nothing else.
3. **Alternate the arms and cool between them.** Sustained decode throttles: a
   third round of the same A/B collapsed from 18 tok/s to 9.9. Anything
   measured after ~10 minutes of continuous generation is a thermal reading.
4. **Alternate inside one process where the question allows it.** Four
   concurrent sessions could not resolve a 6% change: the same server gave
   19.51 and 17.64 tok/s on consecutive rounds, and a third round after an hour
   of generation gave 8.50. The in-process selftest runs both arms against the
   same weights in the same minute and separates 4% cleanly. An end-to-end
   arm-per-server A/B is the instrument of last resort, not the first.
5. **Compare the output bytes.** Every number here comes with `cmp` against the
   other arm.
6. **`cbs/token` in the decode profile undercounts.** It only counts command
   buffers that go through `ds4_gpu_finish_command_buffer`; it reported 2.9
   while the trace showed 39. Trust the trace.

## Open threads

- **A row-tiled expert kernel**, if concurrent serving ever matters more than
  single-stream decode. The kernel is written and exact; the routing caps it at
  about 6% of a batched row. It does nothing for one stream.
- What remains of the host's window now that the early commit overlaps its
  largest part. The 0.080 ms of binding and encoding the named experts cannot
  overlap anything: the buffer it follows has just finished, which is what the
  wait was for.
- The pacer's magnitude on a **cooled** machine. It is now settled that it
  helps and roughly by how much on a hot one (-5.0%, seven rounds out of
  seven), and `DS4_METAL_GPU_PACER_DYNAMIC` makes that a two-minute run rather
  than four server starts. The intensity sweep - 16 x 2000 against ITERS=500 -
  wants the same treatment, and the harness would need to set TGS/ITERS
  alongside the toggle, since the pacer thread reads them when it starts.
