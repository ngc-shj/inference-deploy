# Tuning DeepSeek V4.1 Flash decode on Apple Silicon

Working notes from optimizing [ds4 (DwarfStar)](https://github.com/antirez/ds4)'s
Metal decode path for DeepSeek-V4.1-Flash Q2, on the branch
`perf/v41-metal-apple` in [ngc-shj/ds4](https://github.com/ngc-shj/ds4).

Box: **MacBook Pro, Apple M5 Max, 128 GB** unified memory, macOS 26.6.2.
Model: `DeepSeek-V4.1-Flash-Q2.gguf`, 340.6 GiB (152 GiB of weights plus 189 GiB
of Engram tables that stay on disk), served with `--ssd-streaming --ctx 32768`.

> Correction: commits `722aee8` and `40f5934` on that branch say the numbers were
> measured on an M3 Ultra. They were not — every number here and there comes from
> the M5 Max above. The commit messages could not be rewritten (the history had
> already been shared), so the correction lives here.

Single-stream decode over this work: **12.17 → 18.11 tok/s**, every step gated on
byte-identical output against the arm it was compared with. The last figure was
taken on a machine that had been hot for hours; the same build measured 19.8 on
a cool one earlier in the day.

The largest single win came last and from the least expected place. The gap
between one layer's command buffer and the next is 0.558 ms, and this document
spent most of its length treating that as the cost of the readback. The readback
is 0.15 ms of it. **The other 0.40 ms is the host**, and most of that turned out
to be two waits it did not need:

| | before | after |
|---|---|---|
| `missing_bind` per split layer | 0.355 ms | 0.033 ms |
| `missing_wait` per split layer | 0.291 ms | 0.000 ms |
| host work per layer | 0.402 ms | 0.233 ms |
| throughput (hot machine) | 15.35 tok/s | 18.11 tok/s |

The first wait was for a cache slot: the cache is indexed by expert, so
installing an expert whose slot the GPU is still reading drained every command
buffer in flight. Under zero-copy there is nothing to wait for — the buffers are
already mapped and only the bookkeeping wants that slot — so the entry goes into
one of eight spares per layer instead (`559e89a`, +4.4%).

The second was worse: after submitting the cached experts, the host waited for
that command buffer to *complete* before encoding the pass for the ones it had
to fetch. Command buffers on one queue run in the order they were committed, so
the missing pass could never have overtaken the resident one. The wait bought
nothing (`5888313`, +18%).

## The finding that ties the rest together: host round trips per token

Same kernel, same data, same total work — only the packaging differs
(`iq2bench`, the expert matvec on its own, 40 dispatches of a 1536×5120 IQ2_XXS
gate/up pair):

| how the 40 dispatches are issued | GPU time | effective |
|---|---|---|
| one command buffer, back to back | 0.79 ms | 205.8 GB/s |
| 40 command buffers, no host gap | 6.44 ms | 25.2 GB/s |
| 40 command buffers, 100 us gap | 7.18 ms | 22.6 GB/s |
| 40 command buffers, 300 us gap | 9.95 ms | 16.3 GB/s |
| 40 command buffers, 600 us gap | 13.82 ms | 11.7 GB/s |

**Splitting the work into one command buffer per dispatch costs 8x before a
single microsecond of host gap is added**, and the 600 us gap a decode actually
has takes it to 17x. The host sleeps are subtracted from these times, so this is
GPU-side cost only.

It is not the packaging, though. Two controls settle what it is:

| | GPU time | effective |
|---|---|---|
| one buffer, a barrier between every dispatch (no concurrency) | 0.79 ms | 204.5 GB/s |
| one buffer, the host signalled between every dispatch (`encodeSignalEvent` + `encodeWaitForEvent`) | 6.69 ms | 24.2 GB/s |
| 40 buffers, host round trip between every dispatch | 6.73 ms | 24.1 GB/s |

Serialising the dispatches inside one buffer costs nothing. Stopping for the
host costs the same whether the work is in one command buffer or forty. So the
unit of cost is **the round trip to the host — about 0.15 ms of GPU time each**
— and `encodeWaitForEvent`, which the header calls a pause rather than a
resubmission, does not avoid it.

ds4 makes about **40 of those round trips per token**, one per layer, because
only the host can page in an expert the router picked that is not cached. That
one fact accounts for both halves of the decode: the 28 ms the GPU spends idle
*and* the 136 GB/s it manages while running, which is what this same kernel does
at that duty cycle. It is not the kernel's instruction mix, not memory
bandwidth, and not the power state.

It also explains the failures above. The speculative resident pass and moving
the shared expert after the signal both kept the round trips exactly as they
were, so neither could have helped.

### Why the round trip is there, and what unified memory does and does not buy

An expert-sized (9.49 MiB) no-copy view over a cold part of the file, measured
against the same view once its pages have been touched:

| | cost |
|---|---|
| creating the view | 0.02–0.04 ms |
| first GPU read of it (pages not yet GPU-resident) | 1.0–4.8 ms |
| reading it again | 0.20–0.91 ms |
| a **new** view over the same, already-resident pages | 0.28–0.80 ms |

Two things follow. First, a fresh view over pages that are already resident
costs the same as re-reading the old one, so ds4 making a new view per miss is
not the waste it looks like — the expense is the one-time residency, not the
view. Second, that first read moves 9.49 MiB in 1.7 ms, which is 5.5 GB/s on
memory that does 600 GB/s: **99% of it is page bookkeeping, about 0.7 us per
4 KiB page, not data movement.** Unified memory removed the copy — ds4 reads
weights in place at full bandwidth — and left the mapping cost behind.

### Why the round trip cannot simply be dropped

Three measurements settle it.

**The data is already in memory.** `mincore` over every missed expert during a
384-token generation: **100% of their pages were already resident**, across
47,400 misses. A cache miss in ds4 means the expert is not in *its* address
table, not that anything has to come off the SSD. The round trip is
bookkeeping, not I/O.

**Making everything addressable is free.** One `mmap` of the whole 340.6 GiB
file takes 450 ms, and carving **15,360 no-copy buffers out of it takes 43 ms —
2.8 us each**, with the process footprint unchanged (0.12 GiB at 256 buffers,
51 GiB still free). A full expert address table could be built at startup. The
earlier attempt at one measured 0.04 tok/s, but creating the buffers is not what
costs.

**What costs is that the pages cannot be given back.** A buffer's pages are
wired when the GPU first touches it, and `setPurgeableState:` — the one API for
handing memory back — is ignored for no-copy buffers:

| buffer | set Volatile | state afterwards |
|---|---|---|
| allocated by Metal | previous: NonVolatile | **Volatile** |
| `newBufferWithBytesNoCopy` | previous: NonVolatile | **NonVolatile** |

So addressability and a bounded resident set cannot both be had. Bounding the
resident set means releasing buffers; releasing them invalidates addresses; and
the GPU cannot know which addresses went stale. Somebody has to tell it, once
per layer, and that somebody is the host.

ds4's expert cache plus its per-layer readback is what that constraint forces.
The 6 ms/token of round trips is not waste to be removed — it is the price of
running a 152 GiB expert set through 128 GB of memory.

That conclusion stands, but it was the wrong thing to have been optimising:
the readback is 6 ms of a 52 ms token, and the host's own work around it was
16 ms. Removing two waits from that window was worth more than every attempt at
the readback put together.

The expert cache hit rate is **0.850** (88,385 hits against 15,646 misses over a
384-token generation, 7,498 of the model's 15,360 experts resident). A layer
needs six lookups, so only 0.85^6 = **38%** of layers are clean — merging layers
optimistically and redoing the ones that miss would redo almost everything.

## The ceiling this is working towards

Per token the decode must read 6 experts × 9.49 MiB × 40 layers = **2.28 GiB** of
expert weights. The IQ2_XXS matvec measures 387 GB/s standalone at large sizes —
dequantisation is the limit, not the 600 GB/s the memory does — so:

```
floor, if nothing were wasted    2.28 GiB / 387 GB/s = 5.9 ms/token = 170 tok/s
now                              52 ms/token = 19 tok/s
  of which the GPU is idle       28 ms   (all of it between command buffers)
  of which the GPU is running    24 ms   (2.28 GiB at ~136 GB/s effective)
```

Both halves are roughly equally far off. Removing every idle gap alone caps out
near 2x; the running half is 4x off its own standalone ceiling. Neither is
enough on its own.

## Where a decode token goes

Measured with `DS4_V41_DECODE_PROFILE=1` and an Instruments Metal System Trace
(`metal-gpu-intervals`), on the shipping configuration, warm cache:

| | ms/token |
|---|---|
| MoE | ~46 |
| pre-MoE | 1.7 |
| logits | 1.3 |
| engram | 0.7 |
| everything else | 1.0 |
| **total** | **~52** |

The GPU is busy for **46%** of that. The other 54% — about 28 ms per token — is
idle, and all of it sits **between command buffers**:

```
command buffers            ~39 per token (one per layer)
gaps inside a command buffer   none (busy ratio 1.00)
gaps between command buffers   6928 ms of the 6963 ms of idle
CPU->GPU submission latency    median 564 us, p90 1248 us
kernel duration                median 181 us
```

A layer's work is submitted, and the GPU takes longer to *start* it than to *run*
it. What the submission latency is spent on has not been established. The
per-layer command buffer comes from the router: the kernel picks six experts,
and the host has to learn which, because only the host can bring an uncached
expert in from the file.

A CPU profile of the decode thread says the same thing from the other side —
of 9772 samples, 7666 are blocked in `waitUntilSignaledValue`. Encoding costs
about 30 samples. **The host is not encoding, it is waiting.**

## What the submission latency is made of

It is not a fixed cost. Keeping the GPU busy halves it:

| | GPU busy | submission latency (median) | gap between command buffers |
|---|---|---|---|
| baseline | 46.4% | 564 us | 558 us |
| with the pacer | 43.9% | 283 us | 248 us |

So the latency is not a fixed cost, and something about keeping the queue busy
halves it. *Why* is not established, and the obvious explanation is now ruled
out: on the current build the GPU already spends most of a decode at its top
performance state, and the pacer barely moves it.

| performance state | without the pacer | with the pacer |
|---|---|---|
| Maximum | 64.8% | 69.0% |
| Medium | 17.9% | 14.7% |
| Minimum | 17.2% | 16.3% |

An earlier trace of this decode — before the queue gating, zero-copy reads and
BF16 fusion — had it at the **minimum** state 58.7% of the time, and that figure
was quoted for a while after it stopped being true. Four points of extra
Maximum residency does not explain +10% throughput and a halved submission
latency; what does is not known.

## What worked

| change | effect |
|---|---|
| Read streamed experts where they lie (`DS4_METAL_ZERO_COPY_EXPERTS`) | no copy into slabs; mmap views read at 599.8 GB/s |
| Round the HC weighted sum to BF16 in the kernel that produces it | drops a whole pass at three sites |
| Batch sessions through one readback | 4 sessions: 19.67 tok/s aggregate |
| Parallel Engram reads from 2 rows up (was 256) | decode reads 48 rows, never 256 |
| **GPU pacer** (`DS4_METAL_GPU_PACER=1`) | **+10%**: 17.99/17.62 → 19.84 tok/s |
| **Spare cache entries instead of draining for a slot** | **+4.4%**: 14.71 → 15.35 tok/s |
| **Dropping the host wait for the resident pass** | **+18%**: 15.35 → 18.11 tok/s |
| **Committing the expert dispatches instead of holding them** | **+5.9%**: 52.95 → 50.01 ms/token |

Single-stream decode on a real 256-token generation, cooled, arms alternating:

| | tok/s |
|---|---|
| no flags, as the launch command in this file has it | 15.19, 18.02 |
| `DS4_METAL_GPU_PACER=1` + `DS4_METAL_V41_EARLY_COMMIT=1` | **20.45, 19.97** |

The pacer is the larger half of that and is not new; it was in "What worked"
and not in the launch command.

**The selftest's numbers are not these numbers.** It decodes the same sixty-odd
positions repeatedly from a short context, so its single-step time — 41.85 ms,
which reads as 23.9 tok/s — is about 18% better than a real generation whose
context keeps growing. It is the right instrument for a ratio between two arms
and the wrong one for "what is the throughput", and the difference was reported
as the latter before it was checked.

The pacer runs throwaway ALU work on a second queue while the main queue is
busy, and stops on its own after 20 ms of quiet. It is worth tuning, not
scaling: 16 threadgroups x 2000 iterations gives +10%, 64 x 2000 gives nothing,
and 16 x 8000 costs 28%. Which property of the pacing does the work — the rate
of submissions, the occupancy, something else — is not established; only the
shape of the curve is measured.

The last two are described at the top. Both were found by timing the window
between the readback returning and the layer's work being submitted
(`DS4_METAL_HOST_LAYER_MS`), which nothing had measured before: it was 0.5 ms a
layer, 20 ms a token, larger than anything else on the table.

## What did not work

- **Speculating the resident experts before the readback.** The masked
  address-table kernel reads the real ids and skips uncached lanes, so the pass
  is correct whatever the router chose. Rejected in `722aee8` on two runs a side
  of a 512-token generation — 17.86/17.82 against 18.48/18.27 tok/s — which is
  an instrument this file now knows cannot resolve three percent, and on the
  grounds that the round trip count was unchanged, which the idle decomposition
  has since made the wrong criterion. **Re-measured properly: −0.1%**, seven
  alternating rounds in one process, identical argmax, with the path printing
  that it ran.

  That last part matters. The first re-measurement ran both arms without the
  path at all: its gate wants a non-empty slab count and
  `DS4_METAL_ZERO_COPY_EXPERTS` leaves that at zero — the trap described in the
  measurement section below, walked into by the person who wrote it down.

  The verdict stands, for a reason the original did not give. The idle is a
  committed buffer waiting, not the GPU starved, so moving GPU work earlier
  inside a buffer that is already committed changes nothing. The readback is
  what has to go, not its position.
- **An `MTLResidencySet` for the expert slabs instead of naming them per
  dispatch.** No measurable change.
- **Spinning on the shared event** instead of sleeping: 54.5 → 59.4 ms/token.
- **A full expert address table** (all 384 experts per layer addressable):
  0.04 tok/s. See the next section for what that actually costs.
- **Moving the shared expert after the selected-id signal**, so the GPU has
  id-independent work to run while the host wakes: 15.03/14.58 against
  15.85/15.22 tok/s. The traced arm issued about 16% more command buffers per
  token than the baseline arm; whether that is what cost the throughput is not
  established. Reverted.

## A no-copy window over the file is an eager load, not a lazy map

`newBufferWithBytesNoCopy` over a range of the mmapped GGUF returns in about a
millisecond, but the **first GPU access to it pulls the whole range in**:

| window | first access | implied rate |
|---|---|---|
| 4 GiB | 695 ms | 5.8 GB/s |
| 16 GiB | 2667 ms | 6.0 GB/s |
| 40 GiB | 11244 ms | 3.6 GB/s |
| 64 GiB | 16105 ms | 4.0 GB/s |

Linear in the window, at this SSD's read speed. Afterwards every read of that
window costs the same whether or not the host ever touched the pages
(0.20–0.32 ms for a 9.49 MiB expert either way).

This kills the design where the kernel addresses any expert arithmetically out
of two or three large windows and the per-layer readback disappears: the
windows would have to cover 152 GiB of experts on a 128 GB box, and creating
them means reading all of it. It is also why the full address table measured
0.04 tok/s — the cost was the mapping, not per-page faults. ds4's shape — a
small no-copy view per expert, with the host issuing readahead first — is the
one that fits this behaviour: each view wires 9.49 MiB, and the host has
usually already pulled those pages.

The consequence for the idle time: the per-layer readback is structural. Only
the host can make an expert's pages resident, and it cannot know which expert
without the router's ids.

### Remapping the pages under a live buffer does not reach the GPU

The way around an eager window would be a small fixed window whose pages are
swapped for whichever experts are wanted — bank switching. `mmap(MAP_FIXED)`
over the range a no-copy `MTLBuffer` already wraps does not do it:

| | host sees | the existing buffer's kernel sees | a buffer created after the remap |
|---|---|---|---|
| bank at 60 GiB | `c9adfa79` | `c9adfa79` | `c9adfa79` |
| remapped to 90 GiB | `92c269de` | `c9adfa79` | `92c269de` |
| remapped to 120 GiB | `c2d10376` | `c9adfa79` | `c2d10376` |

The buffer keeps what it was created over. Nothing fails — no error, no crash,
just the old bytes, which makes this a silent-corruption trap rather than an
unsupported call.

What the documentation actually says is nothing: the SDK header describes
`newBufferWithBytesNoCopy:` only as "create a buffer by wrapping an existing
part of the address space", and says nothing about changing the mapping
underneath. `didModifyRange:` is for managed storage and does not apply on
Apple Silicon. So this is measured behaviour of this OS and driver, not a
documented contract.

Metal's own mechanism for this is **placement sparse** (macOS 26 / Metal 4:
`updateSparseBufferMappings`, `MTL4UpdateSparseBufferMappingOperation`,
`placementSparsePageSize`), which remaps a sparse resource's pages onto heap
memory. Heap memory, not file pages — so using it means copying experts from
the file into a heap, which is the slab design again, with stable addresses.
Not tried.

**Indirect command buffers** are not tried either, and on this evidence not
worth trying: an ICB removes host-side encoding, and host-side encoding is 0.3%
of the decode thread. The hardware supports them (compute ICBs and their memory
barriers need Apple3, residency sets Apple6, and the ICB length is unlimited),
so the option stays open if the balance ever shifts.

## Three ways to remove the readback, and why each loses

The readback exists to rewrite an address table. That is a fact about the
current design, not a law, so all three alternatives were built and measured.

**A full address table** — every expert addressable, so nothing to rewrite.
Works, output byte-identical, round trips drop exactly as intended (40 → 32 per
token at 8 layers, counted). Slower at every size: 12.22 tok/s at 4 layers,
11.42 at 8, 8.99 at 19, against ~15-18. Two costs. The layer can no longer use
the deferred split, so it computes all six experts in one pass instead of
starting the cached ones while the host fetches the rest. And every buffer it
can reach must be declared resident: dropping the residency set makes it 15%
faster (11.89 → 13.71 tok/s) **and changes the output**, because the kernel
then dereferences addresses whose pages the GPU was never given. Reads only,
of our own mapping, so nothing is corrupted outside the answer — but it is a
silent wrong answer, so that combination now aborts instead.

**Placement sparse** (macOS 26) — permanent addresses, physical pages mapped
only where wanted, one resource instead of 46,080. Everything about it works on
this machine:

| | cost |
|---|---|
| 152 GiB placement sparse buffer over the whole expert set | 1.1 ms |
| placement heap | 0.3 ms |
| mapping one expert's 38 tiles (256 KiB each) | 0.003–0.05 ms |
| filling one expert by GPU blit from the file mapping | 0.455–1.155 ms |

The mapping update is an order of magnitude below the 0.15 ms round trip it
would replace. What it cannot avoid is a copy: a sparse buffer's pages come
from a heap, and a heap cannot be made out of pages that already exist, so the
file bytes have to be moved. Against **0.03 ms** to wrap those same bytes in a
no-copy view, filling by blit is fifteen times worse, on roughly 36 misses a
token.

The storage modes are worth writing down, because the first attempt guessed
them wrong: the sparse **buffer** must be Private (Shared asserts with "Invalid
Storage Mode 0 for Placement Sparse Buffer"), but the **heap** backing it may
be Shared, and a buffer placed in a shared heap hands back a CPU pointer the
host can write through. So the fill does not have to be a GPU blit. It does not
help:

| filling one expert into sparse heap memory | cost | rate |
|---|---|---|
| GPU blit from the file mapping | 0.455–1.155 ms | 9–22 GB/s |
| host `memcpy` from the file mapping | 0.551–0.646 ms | 15–18 GB/s |
| host `pread` straight from the file | 0.771–3.646 ms | 3–13 GB/s |
| **what ds4 does instead: wrap the bytes in a view** | **0.03 ms** | — |

Writing 9.49 MiB at 16 GB/s on memory that reads at 600 is the same story as
the 0.7 us per page above: the destination pages are new, so the cost is
faulting and accounting for them, not moving bytes. At roughly 36 misses a
token that is 20 ms/token to save 6 ms of round trips.

So placement sparse works in every respect — permanent addresses, one resource,
mapping updates an order of magnitude cheaper than the round trip — and still
loses, because it has to move the data at all. That is the line every
alternative crosses and ds4 does not.

**Bank switching** with `mmap(MAP_FIXED)` under a live buffer — covered above:
the GPU keeps the pages the buffer was created over, silently.

What the three have in common is that the round trip is the cheapest way found
to avoid moving data. Unified memory's gift is that the file pages *are* the
memory; every design that gives that up pays more than the 0.15 ms it saves.

## Speculative decoding: three assumptions, two of them wrong

The plan was to get more tokens out of one pass over the weights. Verify k
drafted tokens as k rows of one batch, and an expert's 2.28 GiB a token is read
once for all of them instead of once each. That rests on three things, none of
which was safe to assume: that the batch path takes consecutive positions of one
session, that a rolled-back session reproduces its own output, and that k rows
cost less than k single steps. All three are now measured. The first is true,
the second was false for a reason worth knowing, and the third is true but by
far too little.

`ds41_graph_step_batch` does take consecutive positions of one session: that is
what `prefill_rows` already means, and `ds41_graph_short_prefill` already calls
it that way. Two things stood in the way of using it as a verifier. `prefill_only`
conflated "consecutive positions" with "publish only the frontier row", so a
verifier could never see the k sets of logits it exists to compare. And under
streaming the batch skipped `ds41_moe_batch` and ran the rows through the
single-row expert path one at a time — the opposite of sharing.

### The rows do not share the weight read, and the address table does not change that

Metal already holds a batched streaming expert path whose conditions match V4.1
Flash exactly — `n_expert == 6`, gate `IQ2_XXS`, down `Q2_K`, 2 to 800 rows —
and it had never run on this model. `ds41_moe_batch` passes
`force_resident = true`, which is right for a large prefill's sequential
whole-layer read and wrong for a batch of four, and nothing else asked for it.
Wiring it up (`DS4_METAL_V41_BATCH_STREAM_EXPERTS`) is correct: output bytes
identical across four concurrent sessions, and identical argmax over 192
verified rows.

It is also worth very little.

| k | per-row experts | address table | |
|---|---|---|---|
| 4 | 159.10 ms/step | 152.89 ms/step | −3.9% |
| 8 | 299.25 ms/step | 279.73 ms/step | −6.5% |

The table stages the union of the rows' selections — 15.8 unique experts of 24
at k=4, 24.6 of 48 at k=8 — so a third of the *staging* disappears. A third of
the *read* does not, and that is the whole story: `v41_decode_batch` in
`ds4_metal.m` pins V4.1 to the per-row `mul_mv` kernels for any batch of eight
or fewer, and its comment says why — the grouped matmul changes the reduction
order before V4.1's BF16 and router boundaries. Each row therefore re-reads its
own six experts whatever the table staged, and 34% fewer unique experts buys 6%.

The dispatch says it plainly: `pairs = nei0 * nei1` is six slices per row, and
the kernel recovers `(row, slot)` from `tgpig.z`, resolves that slot's expert
address and calls the single-row matvec. Two rows that chose the same expert
stream its weights twice. What the address table removes is the buffer and
address preparation for the duplicates, which is all the 4-6% ever was.

Consecutive positions of one session barely route more alike than four
independent sessions answering the same prompt: 15.8 unique selections of 24
against 16.3 of 23.9. There is no same-context bonus worth collecting.

### What a batched row costs

Medians of three alternating rounds inside one process, so that the machine's
±10% between runs cannot decide the answer. Single-step reference in the same
rounds.

| k | single | k-row step | ratio | marginal row | break-even |
|---|---|---|---|---|---|
| 4 | 50.40 ms | 152.89 ms | 3.03x | 34.16 ms (68%) | accept 76% |
| 8 | 51.63 ms | 272.96 ms | 5.29x | 31.62 ms (61%) | accept 66% |

A row inside a batch costs 61% of a standalone token. Batching amortises the
fixed part of a step — about 30 ms, which is the same order as the 28 ms of
command-buffer idle measured above — and nothing else. Break-even is
`0.61 + 0.39/k` of the drafted tokens, so **no drafting depth brings the
requirement below about 61% acceptance**. Prompt-lookup drafting on generated
code does not reach that, and gating on long n-gram matches only lowers the hit
rate, which dilutes the effect without moving break-even.

Where the marginal row goes, from command-buffer boundaries around each stage
(the totals run high, the shares are the point):

| stage | per extra row | share |
|---|---|---|
| routed + shared MoE | 39.2 ms | 61% |
| per-row attention | 16.5 ms | 26% |
| batched HC / Engram / attention projection | 8.1 ms | 13% |

So the 61% is where the 61% is. Making the expert matvec tile over rows — one
weight load feeding every row that selected that expert — is the only change
with enough room in it to make speculation pay. It is also the change the
current kernel choice deliberately refuses, and the refusal buys the exact
agreement between batch and single rows that every measurement here relies on.

### Row-tiled IQ2: the kernel does pay, and it stays bit-identical

Sharing the weight decode across token rows keeps the result exact, which is
the constraint `v41_decode_batch` is protecting. Each row still adds its terms
in the same ib32/l/j order, and the sign is exactly +/-1.0, so moving it from
`(v*g)*s` to `v*(g*s)` changes nothing. Measured against the kernel the engine
dispatches today, one expert's gate/up matvec, arms alternating:

| tile | today (T x single-row) | tiled | saved | marginal row |
|---|---|---|---|---|
| 2 rows | 0.040 ms | 0.032 ms | 20% | 64% |
| 3 rows | 0.059 ms | 0.042 ms | 29% | 57% |
| 4 rows | 0.079 ms | 0.053 ms | 33% | 57% |

Outputs compare identical at every width.

The layout decides whether this works at all. Holding `yl[TROWS][32]` live
across the output-channel loop spills past two rows and collapses — a 3-row
tile costs 4.06 single-row dispatches, a 4-row tile 8.57. Keeping only the
eight activations the current `l` needs costs a re-read of y per output channel
— 20 KiB a row, cached — and removes the spill entirely.

What this is *not*: a memory win. The untiled arm runs at 307 GB/s here, above
the 205 GB/s this document quotes elsewhere, and cycling a 371 MiB pool of
experts to defeat the cache does not move it. The kernel is bound by the
dequantisation, not the read, so what tiling amortises is the grid lookup and
sign work. That also means the saving is capped by how often two rows pick the
same expert, which is 24.6 unique of 48 selections at k=8: pairing every
duplicate is worth about a quarter of the gate/up time, not a half.

### How much of that the routing will actually give up

The mean of 1.95 rows an expert is the wrong statistic, because only a second
row on the *same* expert saves anything. Modelling a greedy widest-first
pairing against the measured tile costs, over 600 live layers at k=8:

| rows choosing one expert | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
|---|---|---|---|---|---|---|---|---|
| experts, mean per layer | 14.58 | 4.57 | 2.13 | 1.19 | 0.84 | 0.59 | 0.38 | 0.34 |

Fourteen and a half of the 24.6 unique experts are chosen by exactly one row,
and no tile can help them. Width-2 tiling takes the gate/up time to 88.7% of
what it is now; width-4, with three more kernel variants to write, takes it to
81.7%.

Through the stage split — MoE 61% of the marginal row, gate/up the larger part
of it — that is about 6% off the marginal row, which moves break-even from 65%
acceptance to 61%. Four points, for a host-side grouping pass, a tile
descriptor buffer, a dispatch restructuring and three kernel variants. **Not
the lever.** It remains a ~6% throughput gain for concurrent serving at k=8,
where there is no acceptance rate to bet on, and that is the case for building
it if it is ever built.

### There is no in-situ bandwidth gap to go after

It looked like there was. Dividing the coarse MoE stage by the expert bytes
gives about 132 GB/s against the kernel's 307 GB/s standalone, which would have
been the largest number on the table. The in-situ profile says otherwise:
`DS4_METAL_MOE_STAGE_PROFILE` at k=8 reports gate/up at 1.198 ms for 48 pairs
of 6.08 MiB, which is **244 GB/s**, and down at 0.749 ms for 3.87 MiB a pair,
which is 248 GB/s. The kernels keep four fifths of their standalone rate inside
the decode loop. The 132 GB/s was a coarse stage divided by the wrong bytes.

Three things that could have explained a gap were measured and do not:

| | cost |
|---|---|
| address table and `reinterpret_cast` instead of a bound buffer | +3.3% |
| no-copy views scattered over the 340 GiB mapping instead of a compact pool | −0.2% |
| bursts of 6 with a host round trip between them instead of continuous | +3% |

`DS4_METAL_ZERO_COPY_EXPERTS` is vindicated by the second of those: where the
bytes lie costs nothing once the pages are resident.

Splitting the MoE further (`DS4_V41_MOE_SPLIT_MS`, k=8, per layer): router
0.34 ms, shared expert 0.42 ms, routed experts 2.3 ms. The shared expert is the
same 37 MiB for every row and the Q8_0 matvec does dispatch a slice per row,
but at 8 rows that re-read is served from cache and costs 2.1 ms a row — 7% of
the marginal, not the fifth it looks like on paper.

So the marginal row divides roughly as routed experts 37%, per-row attention
26%, the batched pre-attention work 13%, shared expert 7%, router 6%. Nothing
in it is a single large lever, which is the answer to whether speculative
decoding can be made to pay here: not by one change.

### A rolled-back session does not reproduce itself unless the pair carry comes back

Rewinding `pos` and the Engram history is not enough. Re-decoding 64 positions
from 49 gave a different token at offset 44 every time — where the reference had
led second place by 0.447, so not a flipped near-tie — and successive rewound
passes did not even agree with each other. It happens with the batch path
removed entirely, so it is the rewind, not the batch.

`ds41_attention_publish` pools two positions into one compressed entry on the
`ratio == 2` layers, and carries the first half in `previous_kv[owner]` and
`previous_score[owner]`. Those are carried step to step rather than indexed by
position, so `pos` alone does not describe them. `ds41_state_spans` already says
this — it saves them, for owners 0..2, exactly when `pos` is odd — but only the
session save path knew it. Rewinding to position 49 left the carry from position
112 in place, poisoning one compressed entry, which changed nothing until
attention first selected it.

Restoring those six tensors on rewind makes it exact: rollback reproduces its
own output, and the batch agrees with single steps on all 192 rows at k=8. Any
speculative implementation needs this, and without it the failure is silent.

## The host's work between layers is mostly not in the way

`DS4_METAL_HOST_LAYER_MS` still reports 0.218 ms a layer, one selected-id round
trip a layer, against a 52 ms token: 8.7 ms, 17% of the token, and the largest
single item left for one stream. A `sample` of the decode thread agrees on the
size — 9776 samples, 8032 of them parked in `waitUntilSignaledValue`, 1744
(17.8%) doing host work — and says what the host work is:

| | samples | share of host work |
|---|---|---|
| `fcntl(F_RDADVISE)` expert readahead | 211 | 12% |
| `newBufferWithBytesNoCopy` (a `mach_msg` each) | 42 | 2% |
| reusable-cache-entry scan | 16 | 1% |
| the rest: encoding outside the streaming cache | ~1475 | 85% |

The readahead looked like the thing to remove. It is real — 18,768 `F_RDADVISE`
calls and 58 GiB advised in one short run, on pages `mincore` already calls
resident — and it is the largest named piece of the host's work. Removing it
changes nothing: an in-process A/B on
`DS4_METAL_DISABLE_STREAMING_EXPERT_READAHEAD`, five alternating rounds,
measures **+0.2%** with every round between 51.5 and 53.0 ms.

So that part of the host work runs while the GPU is busy and never gates
anything. That does not settle the other 85% — removing a host wait was worth
+18% not long ago, so some of what happens between layers is on the critical
path — but it does say the 8.7 ms is not 8.7 ms of recoverable time, and that
the way to find the part that is, is to remove candidates and measure rather
than to add up a profile.

### Alternating both arms inside one process

`DS4_V41_VERIFY_SELFTEST_AB=<VARIABLE>` runs the single-step arms with that
variable set and unset, round by round, against one set of weights in the same
minute. It settled the readahead question in one run of about a minute, where
an arm-per-server comparison could not have resolved 2%.

It only works for a variable the code reads on every use. `DS4_METAL_GPU_PACER`
is read once, during GPU init: toggling it from here starts nothing, both arms
are identical, and the harness reports a confident 0.6% that means nothing at
all. That number was believed for several minutes. The guard is the one already
written down here — make the change announce itself, and check the announcement
before reading the timing.

### What settled the pacer, after two things that did not

The pacer's +10% above was measured hot, with a server per arm. Re-measuring it
took three attempts and the first two produced numbers that looked like answers.

Starting a server per arm, two passes each, alternating: **54.44 and 53.98 ms a
token without, 48.76 and 56.60 with**. The two pacer runs disagree by 16%. That
is the between-run drift this file keeps warning about, and no amount of
within-run rounds fixes it, because the medians inside each run were tight.

The in-process harness could not toggle it. `ds4_gpu_pacer_start` is called once
during GPU init, so setting `DS4_METAL_GPU_PACER` from inside a running process
starts nothing: both arms ran without a pacer, and the harness reported +0.6%
with a straight face. What caught it was the rule already written down here —
the change announces itself, and `grep` for the announcement found zero
occurrences of `GPU pacer on` in a log that should have had one.

`DS4_METAL_GPU_PACER_DYNAMIC` makes the pacer follow the variable while the
process runs, and announce each start and stop. Seven alternating rounds, with
seven starts and seven stops in the log:

| | unset | set |
|---|---|---|
| median | 62.79 ms/token | **59.63 ms/token** |
| rounds where the pacer won | | 7 of 7 |

**-5.0%**, and unanimous. The absolute numbers are a hot machine — 62 ms a token
against 51 cooled — so the magnitude on a cool one is still open, but the sign
and rough size are not.

## Nothing was submitted while the host encoded the next layer

Splitting the window the host spends between one selected-id wait and the next
— marking it directly rather than adding up a profile — gives four exclusive
parts. The first attempt at this got two things wrong and both mattered.

It ended the window at the signal helper's entry, but the wait is further on:
encoder close, signal encode and `commit` happen in between and delay the GPU
directly. That part turns out to be 0.004 ms, so it changed no conclusion, but
it was not measured until it was.

The one that did change a conclusion: **one window in forty is not a layer
boundary.** After the last layer `ds41_graph_step` drains, computes logits,
reads them back and returns, so that window carries sampling and the caller as
well; layer 13 carries the second Engram upload's own drain. Averaging all
forty together hides both, and the flat 0.218 ms a layer was being dragged by
them. Binned by the layer whose readback opened the window:

| window | count | total | bind+encode experts | graph to next routed call | pre-readback | close+signal+commit |
|---|---|---|---|---|---|---|
| ordinary layers | 7600 | 0.262 ms | **0.173** | 0.083 | 0.002 | 0.004 |
| layer 13 | 200 | 1.229 ms | 0.203 | **1.019** | 0.002 | 0.005 |
| last layer | 199 | **3.213 ms** | 0.175 | **3.031** | 0.003 | 0.004 |

(A 62.8 ms token — the machine was hot. The shares and the ratios between rows
are the point, not the absolute milliseconds.)

For an ordinary layer the host's time is mostly **binding and encoding the
experts the readback just named**, not encoding the next layer's attention —
the opposite of what the three-part split said, because its middle part was
pooling layer 13 and the last layer in with the rest.

What both versions agree on is that nothing is submitted while any of it
happens: the expert dispatches the readback just named sit in an open command
buffer until the *next* layer's wait commits it.

The queue already orders whatever is encoded after a commit — the property that
paid for `5888313` — so committing once the expert dispatches are encoded costs
a command buffer boundary and lets the GPU start the experts while the host
encodes the attention that follows them. Seven alternating in-process rounds,
every one of them favouring it:

| | median |
|---|---|
| holding the dispatches | 52.95 ms/token |
| `DS4_METAL_V41_EARLY_COMMIT=1` | **50.01 ms/token** |

**−5.6%**, and the two arms do not overlap at all: 52.51–53.45 against
49.74–50.34. The greedy choice matches the reference at all 448 positions
checked, and a 256-token generation compares byte-identical against the arm
without it.

The window counter does not shrink when this is on and should not be expected
to. It measures the host's wall time between waits, and the early commit does
not shorten that work; it puts GPU work underneath it. Measuring what is left
of the idle needs a trace, not this counter.

Where the overlap comes from is worth knowing: the graph segment it covers is
0.083 ms on an ordinary layer but 1.019 on layer 13 and 3.031 on the last one,
so **more than half of what the early commit hides is those two windows**. That
also makes the last layer's 3.2 ms — the drain, the logits, their readback and
the sampling that follows — the largest single window in the token and the next
place to look.

It also survives the pacer, which attacks the same idle from the other side:
with `DS4_METAL_GPU_PACER=1` in both arms, the early commit is still worth
**−4.2%**, five rounds out of five. Less than −5.6%, as two changes competing
for the same gap should be.

## What the GPU is doing while it is not working

A Metal System Trace over the busy seconds of decode, filtered to this process
(other processes are in that table — Discord was in the first pass's numbers,
though at 0.5-1.3% of intervals it changed nothing):

| | early commit off | early commit on | on, with the pacer |
|---|---|---|---|
| buffers a second | 665 | 1192 | 2006 |
| GPU busy | 44.8% | 47.9% | 41.2% |
| **idle, as a rate over the window** | **54.9%** | **50.9%** | 59.9% |
| gap median | 558 us | 295 us | 221 us |
| start latency median | 604 us | 562 us | 325 us |
| start latency p90 | 1345 us | 1292 us | 1081 us |

**The GPU is idle over half the time.** That has been the shape of this problem
since the top of the file; the trace says it is still true after everything
above.

The early commit takes the idle from 54.9% to 50.9% of the window — four
points — and halves the median gap while doubling the number of gaps. That is
the -5.6% it measures, seen from the GPU's side.

### Was the next buffer already committed when the GPU went idle?

That is the question occupancy and a gap median cannot answer, and it is the
one that decides what to work on. Every decode buffer's commit time is
recoverable from the same table — `commit = GPU start − CPU-to-GPU latency` —
so for each consecutive pair the idle between them splits three ways, summed
raw over the window with no medians multiplied by anything:

| | early commit off | early commit on |
|---|---|---|
| GPU busy | 45.1% | 49.1% |
| **unsubmitted** — the next buffer did not exist yet | 18.4% (9.7 ms/token) | **12.4%** (6.5) |
| **queued idle** — committed, waiting, GPU not started | **36.5%** (19.2) | **38.5%** (20.3) |
| overlap — committed before the GPU finished | 3.7% | **41.6%** |

The first two sum to the idle rate the gap measurement gives independently —
54.9% and 50.9% — so the decomposition is exact rather than approximate.

**Roughly three quarters of the idle is queued idle.** The buffer is committed,
the previous one has finished, and the GPU still does not start for what works
out at about 320 us per buffer transition, twenty milliseconds of a token.
Host-side encoding is the other quarter and the early commit already took six
points out of it, which is what that change was: starvation converted into
overlap, 3.7% to 41.6%.

That settles which direction is worth work. GPU-resident routing or addressing,
which would remove readbacks and therefore host dependency, is aimed at the
12.4%. The pacer, the queue structure and the GPU's power state are aimed at
the 38.5%, and this is the first measurement that gives them a basis.

### The resident path, built, and why it loses

All the pieces measured well separately. The expert cache in a residency set is
free and byte-identical. A committed buffer can be made to reach a resource the
host decides on afterwards. The masked kernels already skip a lane whose address
is zero, so the first pass can be encoded before anyone knows what the router
chose, and a second address table holding only the repairs makes the fix-up pass
run those and nothing else.

Wired into ds4 behind `DS4_METAL_V41_RESIDENT_LAYER`, one layer is
byte-identical over 256 tokens. All forty layers are byte-identical too — and
**slower**: 16.66 and 16.48 tok/s against 21.06 and 17.10.

The first explanation written here was that this is structural — that the stall
must be encoded unconditionally, so an all-cached layer waits for the host
anyway. That was reasoning, not measurement, and measuring it says otherwise.
An `encodeWaitForEvent` costs nothing if the host has already signalled when
the GPU arrives, and on an all-cached layer the host's work is reading six
integers and comparing them.

What the timing actually says, per layer:

| | |
|---|---|
| host blocked waiting for the router's signal | 0.916 ms |
| host servicing after it | 0.516 ms |
| layers needing a repair | 29.6% |

Both are implementation, not structure.

The 0.516 ms is an average over layers that mostly have nothing to do, so it is
concentrated in the 30% that do — about 1.7 ms each, which is exactly the page
wiring an expert's first GPU touch costs according to the note above. This path
installs a missing expert synchronously through `ds4_gpu_stream_expert_cache_get`,
bypassing the asynchronous loader the normal path uses, which starts the load
and runs the resident lanes while it finishes.

The 0.916 ms is the host blocking from its own commit until the router's signal
comes back — start latency and the router, with the GPU running the pass it was
handed.

So the conclusion is not that the oracles are unreachable. It is that this
first attempt gave back more than it took, in two places that can be named.

### What this trace cannot say

The first reading of it said the idle was command buffer start latency, that
forty readbacks a token times a 550 us median accounted for it, and that the
pacer works by cutting that latency to 325 us. None of those three survives.

Multiplying a median by forty is the same arithmetic that produced a wrong
132 GB/s earlier in this file. The gap rate is measured directly and does not
need it.

And the pacer column above cannot be read as a statement about decode buffers:
its own throwaway buffers are in that count and that median. Labelling its
queue and buffers makes the split possible, and with 14,647 of them separated
out the decode-only comparison is:

| | no pacer | pacer |
|---|---|---|
| **decode buffer duration, median** | **391.6 us** | **385.8 us** |
| **decode start latency, median** | **501 us** | **410 us** |
| queued idle | 38.7% | 29.7% |

**The pacer does not make the kernels faster.** Buffer duration moves 1.5%,
which is nothing: the GPU's rate of work is the same with it and without. What
changes is how long a committed buffer waits to start — 501 to 410 us — and
the queued idle that follows from it.

So the mechanism is dispatch latency, not clocks. Only those two per-buffer
numbers are clean in that table: `unsubmitted` and `overlap` are not
interpretable in the pacer arm, because the pacer's own work occupies the GPU
in exactly the windows those two measure.

## What the forty synchronisation points a token are worth

Every layer runs the same closed loop: the GPU decides the route, the host
reads it back, the host prepares the experts, the host submits them. Forty
times a token. Occupancy, gap medians and start latency all describe that
structure; none of them says what removing it would be worth, and without that
number there is no way to tell whether the structure is the problem or just the
most visible thing about it.

A ceiling for it can be measured directly. Decode a fixed token sequence once
and keep every layer's selected expert ids; rewind, and decode it again with
those ids handed to the host instead of read back. The router still runs, the
experts still run, the same bytes are still read. Seven alternating rounds in
one process:

| | median |
|---|---|
| reading the ids back, as now | 52.01 ms/token |
| ids supplied, no readback at all | **35.76 ms/token** |

**−31.3%**, 19.2 to 28.0 tok/s — *without the pacer, which is how everything
above this line was measured*. With the pacer and the early commit on in both
arms the same experiment measures **−18.2%**, 41.76 to 34.15 ms a token, 23.9
to **29.3 tok/s**. The pacer was already recovering part of what the readbacks
cost, so the headroom left for a resident design is a fifth, not a third. The
arms are nowhere near overlapping
(51.34–57.98 against 34.75–37.67) and **the same argmax at all 448 positions** —
which is not a bit comparison; the selftest compares the greedy choice, not the
logits. The capture holds 2560 id sets for 64 tokens, exactly forty a token, so
the replay covered every layer.

**What this arm actually removes is more than the synchronisation.** The host
has the ids before the GPU has computed the route, so it also does its cache
lookup, its miss handling and the following layers' encoding ahead of time.
This is a perfect oracle with unlimited lookahead, and no implementable scheme
gets that. It is a ceiling, not a target.

It does say the control loop is where the headroom is. It does **not** say what
to build, and in particular it cannot be netted against the full expert address
table's cost: that table is not 15% down on this. Measured with correct
residency it reaches 12.22 tok/s over four layers, 11.42 over eight and 8.99
over nineteen — losing outright, and getting worse with coverage. The 15% in
the section above is a local difference against a configuration that drops
residency and answers wrongly. `31 − 15` is not a calculation.

What the 31.3% needs next is to be taken apart, not spent:

1. the normal path — signal, wait, readback;
2. captured ids, but keeping the command buffer boundary the readback would
   have forced and only skipping the wait;
3. the arm above — full precognition and continuous encoding.

The gap between 1 and 2 is what the synchronisation itself costs. The gap
between 2 and 3 is what buffer consolidation and whole-layer lookahead are
worth, and only the first of those is available to any real design.

## Cutting one layer out vertically

Every experiment above is a patch on `ds4_gpu_routed_moe_one_tensor_impl`,
which in one function does the readback and the command submission, the expert
cache lookup and replacement, Metal buffer creation and residency, kernel
selection and encoding, and a few dozen environment-variable branches. Nothing
in it separates the execution plan from the cache from the synchronisation, so
changing any one of them moves the command buffer structure and the concurrency
as well. The trouble this file records in interpreting its own measurements is
a symptom of that, not of the measurements.

The boundary is also inverted. Selected ids are produced on the GPU, promoted
to host control forty times a token, turned into addresses, and handed back.

`ds4-macos/proto/` cuts one layer out instead and runs the two structures side
by side over identical arithmetic — same kernel, same bytes, same ids, the only
difference being whether the ids leave the GPU:

| all-hit layers | host-driven | resident | syncs left | |
|---|---|---|---|---|
| 100% | 0.708 ms/layer | 0.401 | 0 | **−43.4%** |
| 90% | 0.702 | 0.418 | 5 | −40.5% |
| 75% | 0.704 | 0.440 | 10 | −37.5% |
| 50% | 0.700 | 0.463 | 16 | −33.8% |
| 25% | 0.696 | 0.502 | 27 | −27.9% |
| 0% | 0.700 | 0.536 | 39 | **−23.4%** |

Byte-identical output at every row.

**There is no break-even to clear.** The bottom row is the interesting one:
even when every layer misses and has to synchronise anyway, keeping the ids on
the GPU is worth 23%. The synchronisation is not the whole cost — the host
interpreting the route and constructing the dispatch is the rest, and that goes
away whether or not a miss forces a round trip. The hit rate decides how much,
not whether.

At the hit rate this model actually runs (about half the layers have all six
experts cached) the slice says −33%.

### What the prototype is still optimistic about

- It runs the gate/up IQ2 pair only: no Q2_K down projection, no shared expert,
  no attention. The percentages would be diluted by the rest of a real layer.
- A miss costs a synchronisation but not the work of bringing the expert in.
- **The resident arm is told where the misses are.** A real implementation
  learns that only by reading the miss record, so it cannot place its segment
  boundaries this way. That is the next thing to solve, and it is a design
  question rather than a tuning one: either the GPU signals a miss, or the
  token runs to the end and the affected layers are repaired, or the host polls
  a record it does not block on.

### The residency question the slice rests on

The slice assumes a miss can be serviced without the commit, the readback and
the re-encode. That rests on Metal letting a residency set change while a
command buffer is already in flight, which nothing here had tried and which the
API documentation does not quite promise.

`ds4-macos/proto/residency.m` tries it. A single command buffer encoding

    resident pass -> signal gpu_event -> wait cpu_event -> dereference addr_table

is committed *before* the CPU has decided what that address will be. The CPU
wakes on the signal, makes a `newBufferWithBytesNoCopy` over a region of the
340 GiB file, adds it to the residency set, removes what the GPU is already
past, commits the set, writes the address table and signals back.

| | |
|---|---|
| commit / wait / re-encode, as now | 1.966 ms/step |
| one buffer, event-gated | **0.990 ms/step** |
| | **−49.7%** |

Checksums identical against a direct binding, no command buffer errors, no
whole-window first touch, and unchanged at a cache cap of 4 with 36 evictions
— so a *bounded* cache, not a permanently resident everything.

The resident pass between the signal and the wait is what makes this a result.
Without GPU work in that window the same experiment measures **−6%**: the event
gate is then the same stall wearing a different shape, and the CPU's service is
hidden behind nothing. That is also why this is a different experiment from the
full address table above, which grew one residency set per layer forever and
pre-touched every expert. What it rejected was *every address resident*; a
fixed table over a bounded cache, updated under a stalled buffer, is not the
same design and had not been measured.

### Existing pieces, and what they are not

Two of the three parts already exist in `ds4_metal.m` and work:

- a GPU-side cache table lookup — the hit validator kernel;
- masked expert execution that skips uncached lanes — the split path, on by
  default through `DS4_METAL_STREAM_SPLIT_MIN_MISSING`.

The third does not. `ds4_gpu_stream_expert_cache_validate_selected` ends with
`ds4_gpu_end_commands()` — commit and wait — and then reads the selected ids
back out of the status buffer. It moves the hit/miss decision onto the GPU and
keeps the round trip, so it is a different way to spend the readback rather
than a way to avoid it. Only its lookup kernel is reusable for a resident
design.

## What a resident design is worth on a real generation

The selftest's oracle is a ratio at a short context. On 256-token generations
with the pacer and the early commit in every arm, alternating, all five outputs
byte-identical:

| | tok/s | against the base |
|---|---|---|
| base | 18.98, 18.39 | |
| **every layer's ids replayed** | **24.59** | **+31.5%** |
| **replayed only where all six experts are cached** | **21.63** | **+15.7%** |

The fast path fired on **70.4%** of layers — measured over the generation, not
inferred from a census, and higher than the 49% a short sample suggested
because the cache warms as the run goes on.

Two things in that table are worth reading carefully.

Seventy percent of the layers skipping their readback recovers half the
benefit, not seventy percent of it. A layer that misses does not just pay for
itself: its synchronisation stalls what follows. That is the same sub-linearity
from the other side — hiding a miss is worth more than its share.

And **the hits-only row is a floor, not a ceiling.** It makes a miss layer pay
the full commit, readback and re-encode. A resident design does not have to:
the residency experiment above stalls a committed buffer on an event while the
CPU services the miss, and the resident experts run underneath that stall. The
service is a no-copy view and a residency update, tens of microseconds against
a resident pass of a couple of hundred. So the design sits between 21.63 and
24.59 rather than at the bottom of that range, and the earlier guess in these
notes that miss layers would halve the prize was wrong for the same reason.

## One command buffer a token

The resident path's real shape. It had been flushing every layer, which throws
away what it was for: with the ids never leaving the GPU, and the graph already
draining only twice a token, a whole token fits in one command buffer and the
service thread works underneath it.

| | normal | resident, flushing | **one buffer** |
|---|---|---|---|
| decode buffers a token | ~58 | ~40 | **1.9** |
| buffer duration, median | 386 us | 754 us | **22.1 ms** |
| **queued idle** | **29.7%** | 21.6% | **1.7%** |
| unsubmitted | 25.2% | 4.8% | 6.8% |
| GPU busy | 45.9% | 73.7% | 87.8% |

Byte-identical over 256 tokens. Structurally this is everything the idle
decomposition asked for: the per-buffer scheduling cost that was 29.7% of the
window is gone.

**And throughput moves 4.6%**: 19.52 and 19.80 tok/s against 18.62 and 19.03
with the pacer off, and nothing at all with it on.

That is the result, and the lesson is about the instrument. Queued idle was the
largest single item in the decomposition and removing almost all of it bought
almost nothing, so it was not time the token was waiting on — the GPU was idle
in those windows but the token was not blocked by them. The same caution
applies to the 87.8%: at one buffer a token the trace's intervals span the
stalls inside it, so that figure is not comparable with the 45.9% beside it.

## The resident path and the pacer are after the same idle

A trace of the resident path, decode buffers only:

| | normal | resident |
|---|---|---|
| unsubmitted — no next buffer yet | 25.2% | **4.8%** |
| queued idle | 29.7% | 21.6% |

It does what it was built for: host starvation nearly gone. And it makes no
difference to throughput, 20.1-20.3 tok/s against 20.7.

Three explanations were measured and are not it. The stall's duration: covering
it by running the first pass again — same inputs, same outputs, so the answer
is unchanged — makes it monotonically worse, 20.17 to 19.07 to 17.30, which
prices the stall near 0.3 ms a layer and says the cover costs more than it
saves. The repair pass: dropping it is slower, not faster. The blit's encoder
boundary: no change at all.

What it is: **the pacer was already in that gap.** With it off, the resident
path finally wins — 15.80 and 15.05 tok/s against 15.09 and 14.63, both pairs,
byte-identical. With it on, nothing, because a hole that is already full cannot
be filled twice.

So the two behave as substitutes here, which is consistent with both using
the same interval - forty lines of throwaway dispatch taking, more cheaply,
an idle that six hundred lines of control flow also take. That they are the
*same* idle is the hypothesis this is consistent with, not a result: no
measurement here separates one gap from another. It is worth knowing before
the next architectural change aimed at the same place, and worth re-testing
once the ledger can name the interval.

## Why the readback is the cheap answer, in three measurements

The resident path is built, byte-identical over 256 tokens with all forty
layers through it, with the host off the decode thread entirely — and it runs
at 20.1-20.3 tok/s against the normal path's 20.7. Releasing the event before the GPU can reach it - the
work, the dispatches and the service thread all unchanged - gives 23.6-25.2.

**That arm is an oracle, not an achievable speed.** Breaking the dependency
does not only remove the waiting: the same dispatches then read data a
previous stage has not finished writing, so the arm computes the wrong answer
and its output does not compare. What it bounds is *the time that disappears
if the dependency is ignored* - an upper bound on what any scheme could
recover from this stall, and no evidence that a correct scheme reaches it or
that the readback is the best way to pay for it.

So the question is whether the stall can go. It is encoded unconditionally,
because a layer needs one exactly when an expert it picks is not reachable, and
that is not knowable when the layer is encoded. It could be dropped if every
expert were always reachable. Three measurements say that cannot be arranged
here.

**The model.** A V4.1 Flash layer holds its 384 experts as three contiguous
tensors — gate and up at IQ2_XXS, down at Q2_K — 3.04 MiB an expert a tensor,
**3.52 GiB a layer, 140 GiB for the model.** Contiguity is why the idea is
tempting at all: one buffer a layer would make every expert addressable by
arithmetic, with no table, no miss and no repair.

**Metal.** A single no-copy buffer over 140 GiB is refused outright. Per layer
it is allowed, and making one resident costs about **184 ms a GiB** — 311 ms
for 3.56 GiB, 5894 ms for 32 GiB, linear — whether the pages are warm or not,
and whether it goes through `requestResidency` or `useResource` on the dispatch
(1021 ms cold against 311 ms warm through the set, 305 against 257 through
useResource: the cold figures were the SSD, not Metal).

**The machine.** 140 GiB of experts, 128 GiB of memory. The forty windows
cannot be resident at once, and wiring one per layer per token is a quarter of
a second against a 50 ms token.

So some of what the router picks will not be reachable when the layer is
encoded, a miss has to be repaired inside the layer that produced it, and the
repair needs a synchronisation.

These measurements are **consistent with** up to about 20% of a token being
exposed to the streaming dependency, and with the readback being a cheap way
to pay for it. Neither is established. Until the token ledger closes, there is
no basis for saying that the whole 20% is unavoidable streaming cost, or that
the readback is the best available answer rather than the one tried that did
least harm. What the three measurements above do establish is narrower: full
reachability cannot be arranged on this machine, so *some* synchronisation has
to exist.

What that leaves: the hit rate governs how much *work* a layer does, not
whether it stalls, so a better cache is worth having for its own sake and not
for this. And the idle a stall leaves can be filled with another session's
work, which is worth everything for serving and nothing for one stream.

## A token's ledger does not close yet

`DS4_METAL_ENCODER_TIMELINE=<path>` records one timestamped encoder per
dispatch group with the kernel's name, and a first reading of it was written
here claiming that `mul_mv_q8_0` is 40% of a token, that the routed experts are
a couple of percent, and that the largest lever is therefore the Q8_0 format.

**That conclusion is withdrawn. It does not survive its own arithmetic.**

The routed experts are 2.39 GB a token at this model's shape. The table had
them at 0.64 ms, which is 3.75 TB/s. At the 244-248 GB/s measured elsewhere in
this file they are about 9.7 ms. So most of the routed work was missing from
the ledger, and no share computed against that total means anything.

Three things are wrong with the instrument as it was used, and they have to be
fixed before any share is quoted again:

- **Coverage.** The timeline hooks an encoder only when the command buffer is
  `g_batch_cb`. Anything encoded on a buffer from `ds4_gpu_command_buffer(&owned)`
  is invisible, and the streaming expert path makes those.
- **Double counting.** Durations were summed. Encoder intervals overlap, so a
  sum is not occupancy and 11.77 ms is not 40% of anything on the critical path.
- **Missing records.** The expected dispatch count per kernel was never checked
  against the observed one. Ten calls a token to the down kernel where there are
  forty layers should have stopped the reading before it started.

There is also a category error in the reasoning. The cost of a readback, of
residency, of a control path shows up as GPU *gaps*, not as kernel duration.
"The largest kernel is Q8_0" and "the per-layer stall is worth 20%" are
statements on different axes; the first does not touch the second.

### What a ledger has to contain

Before the next claim about where a token goes:

- every queue and every command buffer, with its time range;
- the **union** of intervals per stage, never the sum;
- expected against observed dispatch counts, per kernel;
- bytes and the implied bandwidth, checked against what the machine can do;
- host waiting, GPU unsubmitted, event waiting and I/O, each separately;
- overlap counted once;
- the residual against wall time, stated rather than absorbed.

It closes when the parts sum to the wall clock and the routed experts' 2.39 GB
is accounted for somewhere. Until then the words "bottleneck", "largest lever"
and "a couple of percent" are not available.

The habit this is correcting is more important than the number. Each time a
trace has had a largest column — idle, then the readback, then residency, then
the pacer, then Q8_0 — it has been called the bottleneck and implementation has
followed. A causal model that closes is what stops that, and there has not been
one.

## Calibrating the instrument before trusting it

The ledger above needs a measurement method, and the method itself had to be
audited before use. Seven assumptions were tested against a probe that knows its
own answer: two command queues, a compute-blit-compute command buffer, five
dispatches over two pipelines in one encoder, a command buffer held behind a
shared event, and sleeps of a known 1, 2 and 3 ms at named points. Anything the
trace reports about that probe can be checked rather than interpreted.

Five of the seven were wrong, and the two that held are the two the ledger
now rests on.

**Custom signposts are not in the Metal System Trace template.** A probe
emitting `com.ds4.ledger` signposts under that template records none of them;
the only `os-signpost` tables are Apple's own four subsystems. They do appear
under `Game Performance`, but that template drops the Metal Application
instrument, so the CPU-side command buffer tables come back empty. Recording
`--template 'Metal System Trace' --instrument 'Points of Interest'` is what
gets both: 260 token signposts, 520 command buffer submissions and the GPU
intervals from one run.

**`event-depth` is nesting, not duplication.** The previous analysis filtered
`event-depth == '0'` and so read 65.6% of the encoders in the file. The probe
settles it: it creates exactly four encoders a token, and the trace holds
exactly 1,040 rows for 260 tokens, spread across depths 0, 1 and 2, with no
`(command buffer, encoder)` pair appearing twice. Depth is how far a row is
nested under others that overlap it. Filtering on it discards real encoders.

**`kernelStartTime`/`kernelEndTime` are not GPU time**, whatever the names
suggest. On the probe's gated buffer they span 11.145 ms while the GPU work
inside it is 0.010 ms: they follow the driver's scheduling, and for a buffer
waiting on an event they cover the whole wait.

**The `bytes` column is empty.** A 16 MiB blit reports `bytes=0`. The routed
experts' 2.39 GB cannot be read out of the trace; it has to come from a
dispatch ledger kept on the CPU side.

**A wait on an event is not an interval.** The probe's gated buffer commits at
+0.022 ms and its GPU work starts at +11.680 ms, after the CPU signals at
+11.139 ms. No row covers the gap. Time in which the GPU has nothing to run is
absent from the GPU tables by construction, so it can only be reconstructed
from the CPU side. This is why object labels cannot replace signposts: a label
says which token a piece of GPU work belongs to, and says nothing at all about
the milliseconds in which there is no GPU work to label.

The two that held are load-bearing:

- **`start-latency` is commit to that encoder's GPU start.** Against the
  probe's own commit timestamps, `start - start-latency` recovers the commit to
  a median of 6 us.
- **`GPUStartTime`/`GPUEndTime` agree with the trace exactly.** The API's span
  equals the first encoder's start and the last encoder's end, to a median
  difference of 0.0000 ms on both queues. The two sources can be cross-checked
  against each other, which is the point of collecting both.

The trace clock and `mach_absolute_time` run at the same rate: across an
eight-second capture the offset between the signpost times and the probe's own
log varies by 1.2 us, so a single offset joins the two records.

### What this fixes about the labels

Command buffer and encoder labels reach the GPU rows intact, as
`<buffer label>:<encoder label>`, for blit encoders as well as compute ones,
and a label set *after* the dispatches and just before `endEncoding` still
arrives. Production sets none, so every one of the 45,555 GPU intervals in the
recorded run is unattributable: **semantic attribution coverage is 0%**. The
trace captures the intervals perfectly well - what is missing is any way to say
which token, layer or stage each one belongs to. That is a separate defect from
the internal timeline's `g_batch_cb` blind spot, not the same one seen twice,
and the two must not be added together.

An encoder label describes the whole encoder. Where production puts several
stages in one encoder it will say `stage=mixed`; encoders are not to be split
to make the label sharper, because splitting them is what makes the instrument
change the thing it measures.

## Semantic attribution coverage, before any share of time

`DS4_METAL_LEDGER=<path>` labels every command buffer and encoder and records
the CPU side of the same run; a Metal System Trace with Points of Interest
supplies the times. Output is byte-identical with it off and on. This section
reports only whether the two records agree. No proportion of a token is quoted
here, because a proportion is exactly what was withdrawn above.

One run, 161 tokens whose signpost window lies wholly inside a 12.2 s capture:

| | per token (median) | total | disagreements |
|---|---|---|---|
| command buffers | 43 | 7,586 | 0 |
| encoders | 219 | 35,682 | 0 |
| dispatches (CPU ledger) | 2,736 | 440,036 | 0 |
| encoded signals (expect one a layer) | 40 | 6,440 | 0 |
| GPU intervals inside those windows | | 35,452 | |
| encoders recorded but never seen on the GPU | | | 0 |
| GPU rows naming an unknown command buffer | | | 0 |
| GPU rows whose token disagrees with the ledger | | | 0 |
| GPU rows with no ds4 label | | | 0 |

**Semantic attribution coverage is 100%**, against 0% before. The ledger's
clock and the trace's differ by a constant: over the capture the offset moves
by 5 us, so the two records join without fitting anything.

The counts are the point. A token submits **43 command buffers and 219
encoders**, where the internal timeline watched one. That is why its coverage
could not be repaired by aggregating it differently.

### Expected against observed, per kernel

The withdrawn reading had the routed down kernel running ten times a token
against forty layers. Counted directly, over the same 161 tokens:

| kernel | expected | median | min | max | tokens disagreeing |
|---|---|---|---|---|---|
| `kernel_mul_mv_addr_q2_K_sum6_masked_f32` (routed down) | 40 | 40 | 40 | 40 | 0 |
| `kernel_mul_mv_addr_iq2_xxs_pair_swiglu_masked_f32` (routed gate+up) | - | 40 | 40 | 69 | 0 |
| `kernel_mul_mv_q8_0_f32` | - | 281 | 280 | 281 | 0 |
| `kernel_flash_attn_ext_vec_f16_dk512_dv512` | - | 40 | 40 | 40 | 0 |

The routed experts run once a layer, forty times a token, in every token
measured. The gate+up kernel reaches 69 in the worst token because a miss is
repaired with a second dispatch, and those repairs appear in the ledger as
their own single-kernel encoders, 4.41 a token on average.

### Two more things the instrument does that an analysis has to know

**A GPU interval is not one row per encoder.** Metal coalesces adjacent blit
encoders into a single interval, and the trace joins their labels with `&`:
246 rows in this capture cover 492 encoders. Reading only the first label
loses 240 encoders and calls them missing; apportioning such a row's duration
to each of its encoders would count it twice.

**The `bytes` column is not the bytes.** With `DS4_METAL_ZERO_COPY_EXPERTS=1`
the blits a token does are 89 small copies, 16 and 2048 bytes; the routed
experts are read by the kernels straight out of mapped buffers and move no
bytes through a blit at all. Where the 2.39 GB a token is read from can only
come from the dispatch ledger and the model's shape, never from the trace.

## What the instruments cost, and what the baseline actually is

Three runs of the same prompt, same binary, per-token latency taken from the
streamed chunks so nothing is added inside the process:

| tokens | no ledger | ledger | ledger + xctrace |
|---|---|---|---|
| 0-32 | 19.23 | 18.17 | 16.40 |
| 64-96 | 19.93 | 19.22 | 15.65 |
| 128-160 | 19.57 | 18.95 | 16.96 |
| 160-192 | 18.99 | 18.53 | **10.45** |
| 192-224 | 18.29 | 17.91 | **8.99** |
| 224-255 | 18.16 | 18.03 | 12.02 |
| whole run | **19.21** | 18.49 | 14.84 |

**The baseline is 19.21 tokens a second and was never lost.** The 12.5-15.2
figures that looked like a regression were whole-request throughput with the
prompt's prefill in them; the decode rate underneath was always about 19. The
parent commit measures the same, so there is no regression to find.

**A capture costs 45% inside its window.** The collapse to 8.99 tracks the
xctrace window exactly and recovers after it ends, which is also why nothing
in this file may quote a duration from a traced run.

**The ledger cost 22% until its own tables were fixed.** A token opens 219
encoders, and the encoder table held 4096 slots with tombstone deletion, so
after about nineteen tokens no slot was ever free again and every encoder
creation scanned the table under a global lock. Encoders now live in a
thread-local list - Metal requires single-threaded encoding, so it is exact -
and the command buffer table rehashes and reports its probe lengths: 160,195
lookups at a mean and maximum of one probe. The remaining cost is 3.7%, fine
for counting dispatches and wrong for measuring host idle, so the final A/B of
any change is run with the ledger off.

## Where a token's command buffers come from

Measured with the ledger only, no capture. A token submits **50.7 command
buffers**, and they divide cleanly:

| created by | a token | commit to GPU start (median) |
|---|---|---|
| **the selected-id readback** | **40.00** | 225 us |
| a streaming flush | 7.91 | 222 us |
| beginning a batch | 2.81 | 88 us |

Forty a token is one per layer, and they exist for one reason: the routed
expert selection has to reach the CPU, so the batch is committed, a shared
event is waited on, and a **new** command buffer is made to finish encoding the
same layer. The readback's cost has been discussed in this file as the waiting.
The ledger says the waiting is not the whole of it: each of those forty
buffers then pays a fresh buffer's start latency before the GPU runs anything
in it.

## A token's parts, with the unmeasured left unmeasured

| part | ms | what it is |
|---|---|---|
| command buffer envelopes, unioned | 31.37 | **not GPU work.** `GPUStartTime` to `GPUEndTime` covers the gaps between a buffer's own encoders and any event wait inside it |
| submitted, no envelope open | >= 11.10 | a lower bound on GPU idle with work already committed |
| nothing submitted | 8.70 | host encoding, sampling, I/O |
| token wall | 53.19 | ledger on; 52.05 with it off |

The first row is why no share of GPU time is quoted yet. Splitting the
envelope needs either per-encoder GPU intervals, which only a capture gives and
a capture distorts by 45%, or `MTLCounterSampleBuffer` stage-boundary sampling
on the passes that matter, without splitting any encoder. That is the next
instrument, and it is not needed to choose what to work on.

### The routed experts' own floor

The routed experts are `6 experts x 9.49 MiB x 40 layers = 2.39 GB` a token,
which reproduces the figure the withdrawn reading failed to account for.

| basis | bandwidth | time for 2.39 GB |
|---|---|---|
| current effective, in situ | 246 GB/s | 9.71 ms |
| **best achieved standalone, this machine** | **307 GB/s** | **7.78 ms** |

Both are component figures for the routed traffic alone, and neither is a
floor for a token. 9.71 ms is what today's access pattern gets; 7.78 ms is
what this machine has been seen to do on this shape, which is a demonstrated
target, not a hardware limit. **A full-token floor is not computed**: it would
need the shared expert, attention, the router, the activations and the
synchronisation priced the same way, and none of that is done.

### Headroom

| stage | current | demonstrated target | floor | headroom |
|---|---|---|---|---|
| routed expert traffic | not isolated yet | 7.78 ms | not computed | unknown |
| submitted, no envelope open | >= 11.10 ms | - | **not zero, not measured** | unknown |
| nothing submitted | 8.70 ms | - | not computed | unknown |
| the rest of the GPU work | undetermined | - | not computed | unknown |

**Every headroom in this table is unknown, and an earlier version of it said
otherwise.** Two errors, both the same error:

*The idle was attributed to the readback.* `submitted, no envelope open` is
`token window ∩ committed − union of every command buffer envelope`. It is a
lower bound on idle, and nothing in it says which of the 50.7 buffers is
responsible. That forty of them come from the readback is a separate fact;
putting the two together is assigning a residual to the nearest named thing.

*Its floor was called zero.* `commit` to `GPUStart` contains driver
scheduling, ordering behind whatever is already on the queue, coming back up
from a low DVFS state, and the launch latency that any command buffer pays.
The floor is whatever an empty command buffer costs on a warm GPU and on an
idle one, which is a measurement not yet made. And removing the readback does
not remove the work it stands in for: the expert residency and the miss repair
would still have to happen somewhere. Treating "if this went away entirely"
as a floor makes every stage the biggest one.

## Separating the two switches, and what the pair is worth

The previous version of this section put both switches on at once, read
+11.7% between runs, and called it a result. It was neither separated nor
sound: this machine drifts. Twelve runs of a 2x2 in rotated order came out
monotone in run index and flat in condition by the third round - 19.05, 20.52,
20.95, 21.45, 20.19, 16.77, 16.20, 15.19, 14.99, 14.94, 14.32, 14.67, in the
order they ran. The cause is not heat: `pmset -g therm` has recorded no
warning, while swap sat at 19,291 MB of 20,480 and 94.6 GiB of pages were
inactive. Starting a server that maps a 340 GiB model and fills a 73.5 GiB
expert cache, a dozen times in a row, is what moved the machine.

**An A/B that starts a server per arm cannot measure either switch here.**

`DS4_METAL_V41_EARLY_COMMIT` is read by `getenv` on every layer of every
token, so the in-process selftest can alternate it against one set of weights
in one process. `DS4_METAL_GPU_PACER` is read once when its thread starts, so
it cannot - but holding it fixed for a whole process and alternating early
commit inside gives the interaction, with only the pacer's own main effect
left across runs.

Two servers, nine alternating rounds each, selftest ms a token:

| | pacer off | pacer on | pacer's effect |
|---|---|---|---|
| **early commit off** | 42.40 | 40.07 | −5.5% |
| **early commit on** | 40.23 | 39.10 | −2.8% |
| **early commit's effect** | **−5.1%** | **−2.4%** | |

Both early-commit columns are drift-free: every round separates cleanly, with
the arms' ranges never overlapping (42.22-42.59 against 40.08-40.30), and the
output's argmax is identical over 144 tokens in both.

**The two are substitutes, and the interaction is large.** Additive they would
be −10.3%; together they are −7.8%. Roughly half of what each buys is the same
time, which is what the resident path and the pacer also looked like earlier
in this file - now measured rather than suspected.

The pacer's own effect, −5.5%, is the one number here still taken between
runs. It matches the −5.0% recorded earlier by a different method, which is
some comfort and not a substitute for measuring it properly.

**The pair is worth −7.8% of a token, not +11.7%.** The selftest is a ratio
and runs about 18% optimistic in absolute terms, so it is quoted as a ratio
only.

### What this does not make the pacer

The pacer raises the GPU's performance state by submitting throwaway
arithmetic on a queue of its own. That diagnoses something real - the GPU
drops out of its top state while this workload runs, and during one capture it
spent 30.7% of the time below Maximum - but burning power to avoid waiting is
not an optimisation of the work. Before it could be one it needs energy a
token, sustained performance over ten minutes and more, p95 and p99 latency,
and what it costs a second concurrent stream. None of that is measured. Its
value for now is as a pointer: **why does the GPU fall out of its top state,
and what useful work could occupy the queue instead of filler?**

## How often is the round trip needed? And what the slice did not show

The per-layer readback makes 40 of a token's 50.7 command buffers. Three
designs in this file tried to remove it and each gave up no-copy access to do
it. None asked how often it is needed at all.

`DS4_METAL_STREAMING_EXPERT_TIMING_SUMMARY` answers it, over 418 tokens and
16,720 layer visits. Every figure below comes from that one counter set, whose
parts sum to the whole:

| a layer's six experts | visits | share | a token |
|---|---|---|---|
| **all resident** | 11,877 | **71.0%** | 28.4 layers |
| some missing | 4,777 | 28.6% | 11.4 layers |
| all missing | 66 | 0.4% | 0.16 layers |

`11,877 + 4,777 + 66 = 16,720`, and per layer visit `5.55` experts are resident
against `0.45` missing, which sums to six. So **92.5% of expert selections are
already reachable, and a token misses about 18 of its 240.**

An earlier version of this section quoted `hits=92,793 misses=14,024`, a rate of
0.869 and 33.6 misses a token, from the streaming cache's own counters. Those do
not belong to this population: `92,793 + 14,024 = 106,817` against
`16,720 x 6 = 100,320`, and the 6,497 excess is close to the split path's own
`split_layers=4,570 x missing_experts_avg=1.42`. Two counter sets, one
population, and the numbers were mixed. **Twenty-eight layers in forty needing
nothing from the host is the finding; 0.869 was not.**

### What the slice showed, and the four things it did not

`proto/servemoe.m` takes the oracle out of the resident slice: the router runs
on the GPU, a validate kernel writes the lane masks, the hit lanes run at once,
and a service thread installs what missed. It measures −20% against the
host-driven arm at every hit rate, with identical output and both arms stable
against themselves.

**That is not a result about the control plane, and four claims made from it
are withdrawn.**

**The host is still on the critical path on every layer, including the 71%
that hit.** Per layer the arm signals an event from the GPU, waits on it in the
service thread, writes a value back, and waits for it on the GPU - four
operations, unconditionally, all forty times. The service thread's *work* is
skipped on an all-hit layer; the round trip is not. "The host does nothing on a
hit layer" was wrong; what is true is only that the *encoding* thread never
blocks.

**The repair is not a repair.** It is two pointer stores giving a missing
expert the address of `id % cached`, reusing another expert's bytes. No file
read, no no-copy view, no residency-set update, no eviction, no inflight
protection, no down projection, no page wiring. Both arms therefore read the
same wrong expert and agree; that is a check on the control structure and says
nothing about the model. It also means the flatness across hit rates is
unearned: a miss costs two stores, so of course the hit rate does not matter.
**Against a real fetch it is untested.**

**−20% is not the control plane's difference.** The host-driven arm builds two
command buffers a layer and waits on both - eighty buffers and eighty host
waits a token - against the served arm's one. Command buffer count, host waits,
event waits and dispatch packaging are all inside that number, and none of it
is a comparison against ds4's actual selected-event path.

**The 24 points between −44% and −20% are not the price of the round trip.**
The −44% arm read masks that Metal does not guarantee were visible yet, so it
could call a layer clean and leave its lanes uncomputed. A wrong computation is
not a faster one. What can be said is narrower and is the useful part:
**replacing the CPU's poll of GPU-written memory with an `MTLSharedEvent` made
the arm correct, and it went from −44% to −20%.** The overly broad claim that
Metal orders nothing a running command buffer writes is also withdrawn - what
is unspecified is a *host* read of that memory without a shared event, not the
ordering between passes on the GPU.

### And the main tree already has this path

`DS4_METAL_V41_RESIDENT_LAYER=all` is a service thread, a real miss load, a
repair table, gate, up and down, and a token-scale command buffer. This file
records it at 20.1-20.3 tok/s against the normal path's 20.7. The prototype's
only new part is that a service thread does not interpret the ids on an all-hit
layer, and it pays the same per-layer event round trip. "Integrate this next"
was written without looking, and is withdrawn too.

### What the next prototype has to satisfy

1. **Zero CPU events and zero CPU signals on an all-hit layer**, counted, not
   asserted. Anything else is the existing resident path with a different
   spelling.
2. **A real fetch on a miss**: the expert's bytes, a no-copy view, the
   residency set, the eviction and the invalidation of the id that left.
3. **A control group with the same command buffer structure**, so what is
   measured is the control plane and not eighty command buffers against one.
4. **One difference from the existing resident path**, named in advance.

The `servemoe` harness also has a bug to fix before it is used again: `epoch`
is handled as if it were a flag, and the service thread stores zero to it after
the last layer. With two served tokens in a row that store can land after the
main thread has published the next epoch. The arms alternate today, so the
host-driven stretch hides it. It needs a sequence ring or an explicit
completion acknowledgement.

### What does survive

Three things, and they are worth keeping:

- **71.0% of layer visits need nothing from the host**, from counters that sum
  to their population.
- **A host read of GPU-written memory needs an `MTLSharedEvent`**, demonstrated
  by an arm that was wrong without one and right with it.
- **Checking each arm against itself finds what comparing arms cannot.** Two
  bugs in the shared expert kernel surfaced only that way: a threadgroup fill
  written for 64 threads that puts 4096 bytes into a 2176-byte allocation at
  any wider launch, and a row assignment that is a compile-time function of
  `NSG` and `NR0`, so a host program disagreeing about either has two
  simdgroups writing the same row.

## Abort and resume, and what the ledger says it will cost

An event cannot be skipped. `encodeWaitForEvent` is a command, written into the
buffer before the validator has run, so no design built on shared events can
spend nothing on the 71% of layers that hit. The only boundary Metal gives that
is decided *after* the GPU has looked is the completion of a command buffer.

So: submit the segment, let each layer validate its own route, and on a miss
record `{layer, ids, mask}`, raise an abort, and make every layer after it cost
nothing. The buffer completes; if nothing missed the token is done; if
something did, the host loads the expert for real and submits a continuation
from the failed layer's routed dispatch, reusing the selected ids and route
weights already computed so attention and the shared expert are not repeated.
The host is then involved once per layer that actually missed - about 11.4 of
40 - and the target is `command buffers a token ~ miss layers + 1`.

Two measurements from the ledger say what that costs and what it needs.

**The host is never ahead of the GPU.** Over 12,520 command buffers in 256
tokens, the number of layers the host had already encoded past a buffer when
that buffer's GPU work finished is zero at the median, at p90, at p99 and at
the maximum. Every one of them. The readback does not merely add a wait; it
holds the pipeline exactly serial.

**Given the chance, the host would run to the end of the token at once.**

| a token | |
|---|---|
| host encode, create to commit | **4.97 ms** |
| GPU execution | **29.54 ms** |
| encode as a share of GPU work | **16.8%** |
| the 40 readback buffers alone | 3.99 ms encode, 23.30 ms GPU |

The host encodes a whole token in a sixth of the time the GPU needs to run it.
So a design that lets it run ahead will have all forty layers encoded while the
GPU is still in the first few, and an abort at layer L leaves 39-L layers of
submitted work behind it. **Having the host notice and stop encoding is not a
mechanism - it is far too late by construction.** The layers after an abort
have to cost nothing on the GPU, and that is the piece to build.

### What a resume has to put back

Resuming at a layer's routed dispatch means re-running the layers after it,
which re-runs their attention. Most of what that touches is indexed by layer or
position and is simply overwritten. Two things are not:

- the residual stream at that layer's input - `residual` and `x` at
  `DS4_N_HC * DS4_N_EMBD` and `DS4_N_EMBD`, with `pre`, about 40 KB;
- `previous_kv[0..3]` and `previous_score[0..3]`, 2 KB each, which this file
  already records as carried from step to step rather than indexed by position.
  A layer that ran on garbage advances them, and re-running from L would
  advance them again from the wrong base.

About 56 KB a layer, 2.2 MB for a token held as forty slots: small enough to
snapshot at the top of every layer and restore on a resume.

**Superseded.** No snapshot was needed. The abort stops a layer before its
first state update, so the layers behind it never run, and the continuation
resumes at the failed layer's routed stage - its attention has already run
correctly and its carry must not advance twice. Restoring `previous_kv` would
have been wrong.

### The bar this has to clear

1. **Zero CPU events and zero CPU signals on an all-hit layer**, counted.
2. **A real fetch on a miss**: the existing loader, the eviction, the
   invalidation of the id that left, the residency update.
3. **A control group with the same command buffer structure**, so what is
   measured is the control plane.
4. **Byte-identical output** against the baseline, each arm reproducing itself.
5. **`command buffers a token ~ miss layers + 1`**, counted.
6. **End-to-end token latency in ds4 improves** - without the pacer first, then
   with it, to see whether the two are again substitutes.

None of that is done. What is done is the sizing above, and the finding that
the mechanism has to live on the GPU.

## Abort and resume: 16.14 to 20.95 tokens a second, byte-identical

The readback makes 40 of a token's command buffers and holds the pipeline
exactly serial. An `MTLSharedEvent` cannot replace it, because the wait is a
command written before the validator has run, so it costs the same on a layer
that hits as on one that misses. The boundary decided *after* the GPU has
looked is the completion of a command buffer.

So each layer checks its own route. After the router selects, a kernel reads
the layer's live address table; if an expert has no address it records the
layer, the lanes and the ids, and zeroes the indirect dispatch arguments of
everything encoded after it, so those dispatches issue and launch nothing. The
buffer completes, the host reads a record it can trust, brings the expert in
with the loader the readback path already uses, and re-submits from that
layer's routed stage - not its top, because its attention has run correctly
and its carry must not advance twice.

### What the gate had to be told about the graph

Three things, none of them about the gate:

- layers that read the Engram rows need them written first, which is what made

- the graph drains at layer 13, before layer 14 overwrites the first Engram
  table's shared input;

### A token on the new path, closed inside one run

The previous version of this section subtracted 41.99 ms from 47.73 ms and
called the difference a residual. They are different runs, so it was not one.
Measured instead as parts of one token in a single run, gate on, pacer off,
segment 3, output byte-identical:

| part | ms | of the token |
|---|---|---|
| **GPU command-buffer envelope** | **34.78** | **75.1%** |
| repair: the real loader, eviction, residency | 4.22 | 9.1% |
| GPU not running, inside commit-to-done | 3.29 | 7.1% |
| host encoding | 3.02 | 6.5% |
| tail: logits and their readback | 1.05 | 2.3% |
| cache accounting and prunes | 0.01 | 0.0% |
| **sum against a 46.28 ms wall** | **46.37** | **residual −0.10** |

The parts are exclusive and sum to the wall to within 0.2%. Two things it
settles: the repair is four times the token tail, and it was outside the
segment timings entirely, which is where 18.9 experts a token were being
brought in. And commit-to-done is not the host waiting on a queue: 34.78 of its 38.07 ms
is inside command buffers that the GPU had started and not yet finished.

**That row is an envelope, not work.** It is the sum of `GPUEndTime -
GPUStartTime` over the buffers a drain waits on, so it contains the gaps
between encoders inside a buffer as well as the kernels. 75.1% of a token is
therefore not a utilisation figure, and nothing here says the GPU was computing
for 34.78 ms.

Splitting it needs per-dispatch or stage-boundary counter sampling on the
passes that matter - not a capture, which distorts by 45%. Until that is
measured, the routed experts' share of the envelope is unknown: the 5.47 ms
that 2.39 GB takes at the 437.9 GB/s this file's prototype reaches is a floor
for that prototype's shape, not this path's routed time, and it cannot be
subtracted from 34.78 to conclude anything about the rest.

Removing the host's encoding entirely would now be worth 6.5%, so an indirect
command buffer remains next in line rather than not needed.

### Inside the envelope: the routed experts are a fifth of it

This machine has no dispatch-boundary counter sampling - only stage boundaries,
which would mean splitting the encoders and so changing the submission shape.
So a pass is timed by how much the envelope grows when it is encoded again.
Running the routed passes twice reads the same inputs and writes the same
values, so the answer does not change and the extra time is that pass. Every
row below is byte-identical to the baseline:

| | envelope | |
|---|---|---|
| as it runs | 34.83 ms | |
| routed gate/up encoded twice more | 42.82 | +7.99 for 2, so **4.00 ms a pass** |
| routed down encoded twice more | 40.25 | +5.42 for 2, so **2.71 ms a pass** |

**The routed experts are 6.71 ms of the 34.83 ms envelope, 19.3%.** Against the
2.39 GB a token they move, that is **356 GB/s** - between the 307 this file
measures standalone and the 437.9 its prototype reaches with six lanes in
flight. At 437.9 the same bytes would take 5.47 ms, so there is about 1.24 ms
in them and no more.

**The other 28.12 ms is everything else**: attention, the shared expert, the
router, the norms, and whatever gaps sit between encoders inside a buffer. That
is where the next measurement goes, and it corrects the instinct this file
started with - the routed experts are not the largest thing a token does.

The method's limit: the slope assumes an extra pass costs what the first one
did. For a pass reading 2.39 GB that is reasonable, since none of it stays in
cache, but it is an assumption and not a measurement.

need them timed: bytes times the bandwidth shortfall is enough to rank.

At the 437.9 GB/s the prototype reaches with six lanes in flight, the segment's

**The shared expert's gate and up were the first thing tried**, being two
independent Q8_0 projections of the same input and small enough to get wrong
cheaply. Put in one dispatch with two lanes, 27 paired rounds in one process
give a median of -0.10 ms a token, quartiles -0.27 to +0.16, and the old serial
pair kernel +0.06. No improvement was detected.

That is all it says. It does not say the stage is not lane-limited: each of
those projections already dispatches 1152 threadgroups where `proto/concur.m`
measured its shortfall at 288, so the curve that predicted 0.47 ms was being
read off a shape four times smaller. The prediction was wrong before the
experiment was.

The comparison is also weaker than a byte comparison: the in-process harness
checks the argmax of each step, not the output bytes, runs its arms in a fixed
A-then-B order, and its rewind does not put back the expert cache, so the B arm
inherits whatever the A arm warmed.

### What the attention projections actually reach: about 560 GB/s

Duplicating a pass in place re-reads the same 35-45 MB immediately and times a
replay out of the last level cache, not the pass. A cold sweep instead walks
all forty layers' weights once each, 1.4 to 1.8 GB, through the kernel the
decode path uses, in one command buffer timed by its own GPU span, writing to
scratch:

| | GB a sweep | ms | |
|---|---|---|---|
| q_b | 1.783 | 3.14 | **568 GB/s** |
| output_a, the grouped kernel | 1.426 | 2.52 | **566 GB/s** |
| output_b | 1.783 | 3.20 | **557 GB/s** |

It scales with the bytes, which is what says it is measuring them: two laps of
the same forty weights take 6.53 ms and four take 12.52, for 3.565 and 7.130

All three are kernel-only: `ds41_matmul_rows` rounds to BF16 afterwards, which
the other two do not, so q_b is swept through `ds41_matmul_batch` without it.
With the post-op it reads 568; without, 544 to 562. The difference is noise.

**What it does not establish, and what is withdrawn from the sections above:**

- that the routed experts are the slowest GEMV, or that they would take 4.23 ms
  at 565. Their 7.02 ms came from duplicating a pass in production, which
  re-reads the same six experts a layer immediately - the hot replay this very
  section was built to avoid;
- that the segment's non-routed time is 27.81 ms. That number is 34.83 minus
  the same 7.02, so it fails with it;
- that the non-routed weights are 12.9 ms, or that fifteen milliseconds of the
  segment is not weight streaming. Both are priced off the 27.81, and both
  apply 565 GB/s to shapes that have not been measured - the shared expert, q_a
  at about 640 threadgroups and kv at about 256, which are nothing like the
  three above;
- that the dense GEMV search is over. Three of them are measured. The shared
  expert, q_a, kv, the router and HC are not.

The next measurement is the routed kernel under the same protocol, then the
small shapes. Re-dividing the token's time waits until they are measured rather
than subtracted.

**The new baseline is 46.28 ms a token, 21.61 tokens a second**, which is 12.8%
above the 19.15 this file records as stable and 5.4% above the best it has
recorded at all. From here a change is worth the milliseconds it removes from
46.28, measured in the same run as the thing it is compared with.

## How to measure this without fooling yourself

1. **Discard a warm-up request in every arm.** The first request after a build
   runs ~23% slower than the steady state (63.73 vs 51.68 ms/token for identical
   code) because both the expert cache and the page cache start cold. An A/B
   whose arms each start a fresh server and measure their first request is
   measuring its own run order. Two of the conclusions above were wrong the
   first time for exactly this reason.
2. **Prove the code path ran.** Print a one-shot note from inside the change.
   `DS4_METAL_ZERO_COPY_EXPERTS` leaves the slab count at zero, which silently
   disabled a slab-gated path in *both* arms of an A/B that then looked like a
   22% win — it was the run-order bias, nothing else.
3. **Alternate the arms and cool between them.** Sustained decode throttles: a
   third round of the same A/B collapsed from 18 tok/s to 9.9. Anything
   measured after ~10 minutes of continuous generation is a thermal reading.
4. **The selftest measures ratios, not throughput.** It decodes a short context
   over and over, so its ms/token runs about 18% ahead of a real generation:
   41.85 ms reads as 23.9 tok/s where the same build generates 256 tokens at
   20. Quote it for an A/B and never as the headline.
5. **Do not alternate in one process for an effect with hysteresis.** The
   pacer changes the GPU's power state, and the state outlives the arm: with
   it toggled round by round, its own "off" arm reads 44.2-46.6 ms a token
   while standalone runs without it read 51.3-53.0. The in-process instrument
   then reports -4.3% for something that looks like -17.6% between runs, and
   neither number is the effect. The instrument is right for what is local to
   the work and wrong for what is local to the machine.
6. **Alternate inside one process where the question allows it.** Four
   concurrent sessions could not resolve a 6% change: the same server gave
   19.51 and 17.64 tok/s on consecutive rounds, and a third round after an hour
   of generation gave 8.50. The in-process selftest runs both arms against the
   same weights in the same minute and separates 4% cleanly. An end-to-end
   arm-per-server A/B is the instrument of last resort, not the first.
7. **Compare the output bytes.** Every number here comes with `cmp` against the
   other arm.
8. **`cbs/token` in the decode profile undercounts.** It only counts command
   buffers that go through `ds4_gpu_finish_command_buffer`; it reported 2.9
   while the trace showed 39. Trust the trace.

## Open threads

- **A row-tiled expert kernel**, if concurrent serving ever matters more than
  single-stream decode. The kernel is written and exact; the routing caps it at
  about 6% of a batched row. It does nothing for one stream.
- The last layer's window: 3.213 ms against an ordinary layer's 0.262, the
  largest single window in a token. It is the final drain, the logits, their
  readback and the sampling and caller behind them.
- Binding and encoding the named experts, 0.173 ms on an ordinary layer, which
  cannot overlap anything: the buffer it follows has just finished, which is
  what the wait was for.
- **Wiring the two prototypes into one layer of ds4**: the address-table kernel
  and the split execution already exist, and the service thread pattern already
  exists for the TP gate. What is new is the residency set moving under a
  buffer in flight, and it now measures.
- ~~**Placing the segment boundaries without an oracle**~~ — settled. The GPU
  decides: a validate kernel checks the live address table and switches the
  rest of the segment off, and the boundary is the command buffer's completion
  rather than a signal the host waits on. The segment length is a measured
  knob, best at two or three layers.
- Why a committed buffer waits ~320 us for the GPU to start it. It is three
  quarters of the idle, but it is below the 35.76 ms a token the readback-free
  arm reaches, so it is second.
- ~~The pacer's magnitude on a **cooled** machine~~ — overtaken. With the abort
  gate on, no additional benefit from the pacer was detected and the two are
  not additive, so its intensity is no longer the question. What it is still
  good for is as a diagnostic: it says the GPU leaves its top performance
  state, which the gate does not by itself answer.

## A decode token with a perfect expert cache costs 38.0 ms

The abort gate's per-token accounting now reports a 64-token window at a time
rather than a running mean, alongside the expert cache's own counters. Every
run, both arms, prints the same third window:

```
expert cache over the last 64 tokens: 240.00 hits, 0.00 misses, 0.00 evictions
over the same 64 tokens: 38.13 ms wall, 0.00 ms repair a token
```

That window is a real decode of 64 tokens - 240 routed ids each, the whole
gated segment loop, the same code as every other window. It differs only in
that the cache already holds all six experts of all forty layers. Across ten
runs it is 37.99, 38.08, 38.09, 38.13, 38.19, 38.20, 38.26, 38.37 ms, with two
outliers on a loaded machine.

**This is measured, not subtracted.** It is a floor with the experts in place,
and it prices the rest directly: a saturated steady state runs 50 to 55 ms, so
the miss-and-repair machinery costs 12 to 17 ms of a token.

What that buys per miss is the surprise:

| misses a token | ms of repair | ms per miss |
|---|---|---|
| 0.00 | 0.00 | - |
| 2.33 | 5.2-7.9 | 2.2-3.4 |
| 4.30 | 2.5-11.3 | 0.6-2.6 |
| 5.66 | 4.0-11.5 | 0.7-2.0 |
| 13.14 | 5.5-15.2 | 0.4-1.2 |
| 56.34 | 13.0-41.3 | 0.2-0.7 |

A miss brings in 9.49 MiB. At the 560 GB/s the dense projections reach, those
bytes are 0.017 ms. A miss costs one to three. **So the cost of a miss is
almost entirely not its bytes**, and it falls as misses per token rise, which
is what a per-abort cost looks like: several misses in one layer share one
abort and one resubmit. At the steady state's 5.5 misses a token the gate
reports 7.8 aborts.

### The prefill headroom, lent to decode

Admission reserves 7.12 GiB so a layer-major prefill sweep has room past the
dynamic cache. Decode cannot use it and, once the cache saturates, every miss
is an eviction that space would have prevented - misses and evictions are equal
to the decimal in every window past saturation.

Replaying the route log the validator already writes: at 7,930 entries a
1,162-token generation misses 5.36 times a token, at 8,698 it misses 4.08, and
the floor - ids the run had never seen - is 3.31. Measured over the saturated
windows the same two capacities give 6.01 and 4.78. The simulation predicts the
machine, so it can be trusted for the shape of the curve, which is flat past
about 9,500.

`DS4_METAL_V41_DECODE_LEND_HEADROOM` (default on) lends it, reclaiming it
before each prompt the way `ds41_encoder_acquire` borrows in the other
direction, and moving the budget without clearing the cache. Output is
byte-identical in every arm.

**Its time value is not established.** It removes 1.2 of 5.5 misses a token;
priced at the per-miss cost above that is under 2 ms, and this machine's
run-to-run spread on an unchanged binary is 29% (48.06 to 68.10 ms for the same
window of the same work). Four ABBA runs gave 17.94 tok/s off against 19.56 on,
and a later eight-run batch collapsed to 0.88-17.76 tok/s when back-to-back
servers churned the page cache - those eight are discarded, not averaged.

So the change is kept for its mechanism, which is confirmed, and not for a
speed number, which is not. The lever the floor identifies is the per-abort
cost, not the per-miss bytes.

## What the abort gate did to speculative decoding

The earlier table said a batched row costs 61% of a standalone token at k=8 and
break-even is 66% acceptance. Re-measured on the same harness with the gate on,
three alternating rounds in one process:

| k | single | k-row step | marginal row | break-even |
|---|---|---|---|---|
| 4 | 39.94 ms | 139.89 ms | 33.32 ms (83%) | accept 88% |
| 8 | 40.23 ms | 259.45 ms | 31.32 ms (78%) | accept 81% |

Rollback reproduces its own output in both; batch and single agree on argmax
over 96 and 192 rows.

**The gate made speculation harder, not easier.** Batching amortises the fixed
part of a step, and that is exactly what the gate removed: the single step fell
from 50.40 to 39.94 ms while the marginal row barely moved, so the marginal
row's share rose from 68% to 83% and break-even with it.

The arithmetic closes the question rather than leaving it to a better drafter.
At k=8 the fixed part is 259.45 - 8 x 31.32 = 8.9 ms. Gating the batch verifier
too - the obvious next idea - could remove at most that, 3.4% of the step, and
would not move break-even. The marginal row is 78% because each row re-reads
its own six experts: `v41_decode_batch` pins V4.1 to the per-row matvec for any
batch of eight or fewer, deliberately, because the grouped matmul changes the
reduction order before V4.1's BF16 and router boundaries. No control-plane
change touches that.

## The routed kernel, swept cold

375 GB/s, 6.38 ms for the 2.389 GB a token routes to, against the 7.02 ms the
in-production duplication credited it with. Gate/up alone is 3.91 ms at 373
GB/s, down 2.43 at 382, and they sum to 6.34. Laps of 1, 2 and 4 give 6.38,
12.75 and 25.46 ms - 1 : 2.00 : 3.99 - all at 375 GB/s with a 0.13 ms spread.

The gap to the existing estimate is 0.64 ms, under the 1 ms the search needed.
**The routed kernel is finished as a target.**

Two things had to be fixed before the number meant anything, and both were
caught by counting rather than by the number looking wrong.

The first version reported 4025 GB/s - four times this machine's memory
bandwidth - and scaled perfectly with laps, which rescues nothing. The selected
tensor is a host-written shared buffer, so every dispatch already encoded reads
whatever was written last: forty layers each got the last layer's ids, their
own address tables answered mostly zero, and the masked kernel read nothing.
Each repetition now writes one id set once and sweeps every layer with it.

And the warm-up ran one set while eight others paid their first GPU touch - the
page wiring, about 1.7 ms a buffer, independent of how much is read - inside
their own timed repetition. Every set is now touched untimed, running both
kernels whatever the arm measures. The preload reports what it requested beside
the cache's own install count and an audit of every address the timed region
will follow, and refuses to print a bandwidth if any is zero: 2,160 installs
for 9 sets x 40 layers x 6 experts, 2,160 of 2,160 addresses live before and
after.

The same host-clock check was applied to the dense sweep, whose 560 GB/s this
file relies on. GPU span 3.11 ms against a host wall of 3.40 for q_b: it
stands.

## What a cache miss costs, and what it is not

The gate's report now takes every figure from the same 64 tokens, after the
token's wall is added rather than before, and calls its repair number
`repair-load` because it covers `ds4_gpu_gate_repair` and not the re-encode and
re-commit behind it. Aborts and command buffers used to be running means since
startup while misses were a window, so the two could not be divided by each
other.

Within-run regressions over thirteen windows in each of four runs:

```
wall           = 44.3-53.1 + 0.19-0.38 x misses   R2 0.68-0.85
repair-load    =  1.7-3.2  + 0.20-0.24 x misses   R2 0.77-0.91
commit-to-done = 36.9-46.6 + 0.00-0.14 x misses   R2 0.00-0.85
```

**The marginal miss is a fifth of a millisecond, CPU-side.** The intercepts are
not claimed: the windows span 2.3 to 13 misses and a zero-miss window is a
different regime where `gate_repair` is never called at all.

And the miss is not a page-in. `mincore` moved ahead of the `F_RDADVISE` -
where it used to run after it, measuring the readahead rather than the miss -
sampling one expert in sixteen across all three of its ranges: **92.8% of a
missing expert's pages are already in core**, 88% of ranges fully so. So
pulling the readahead earlier has nothing to pull.

### Two negatives worth keeping

`DS4_METAL_V41_REPAIR_BATCH` brackets a repair's residency edits into one
commit instead of one per allocation, and moves the global prune to the end of
a token instead of once per layer - where thirty-nine of forty returned at the
first line and the one that evicted ran with only layer zero's hotness raised.
ABBA, 700 tokens an arm: commits fall 11.29 to 6.18 a token, which is exactly
one per abort plus one for the accounting pass, and **nothing else moves** -
miss, abort and command-buffer counts identical to two decimals in all four
arms, wall 51.30 against 52.31 ms inside an 8 ms spread. No benefit was
detected at this resolution, so it is off by default.

`DS4_METAL_V41_DECODE_LEND_HEADROOM` lends the 7.12 GiB of prefill headroom to
the decode cache. Replaying the route log the validator writes, 7,930 entries
miss 5.36 times a token and 8,698 miss 4.08; measured, 6.01 and 4.78. The
simulation predicts the machine, and says the curve is flat past about 9,500
and that 3.31 misses a token are compulsory. Priced at the marginal 0.20 ms
that is **0.25 ms a token**, below what this machine can resolve, so it is off
by default too. Even an infinite cache is worth 2.34 x 0.20 = 0.47 ms.

## The marginal miss, corrected: 0.20 ms was the cache still filling

The 0.20 ms above is real but it is not the steady-state price, and every
sizing on this page that used it is wrong by about six times.

In one clean 1,000-token run, split by regime rather than pooled: while the
cache is still filling (tokens under 449, 7 to 28 aborts a window, entries
below the budget) `repair-load` against aborts has a slope of **0.222 ms** -
which is the figure above, arrived at independently. Once the cache is full,
every add needs an evict, and over the last eleven windows the slope is
**1.51 ms**. Two regimes, seven times apart, and the earlier number was
measured in the one that does not describe a long generation.

Re-measured on a quieter day across seven runs, the steady slope of *wall* on
aborts is **1.08 ms an abort** pooled within-run (77 windows, each run centred
on its own mean so run-level drift cannot leak in, R2 0.48), median of the
per-run fits 1.26. An earlier single-run fit said 2.19; that was eleven windows
of one run and is withdrawn too.

So the corrected sizing of the two negatives below: an infinite cache is worth
1.82 aborts x 1.08-1.26 = **2.0 to 2.3 ms a token**, not 0.47 ms, and lending
the headroom is worth 0.92 x 1.08-1.26 = **1.0 to 1.2 ms**, not 0.25 ms. Both
were closed against a number from the wrong regime.

**Do not price a steady-state change with a marginal cost measured while the
cache fills.** The regimes differ in what a miss has to do, not just in how
many there are.

## A dispatch costs 0.70 us, and 2.25 us when the gate sends it indirect

`proto/dispatchcost.m`. Empty kernels, N of them in one command buffer, GPU
span regressed on N; every dispatch increments an atomic and the total is
checked against N, so a shape that launched nothing cannot read as a fast one.
Perfectly linear from 256 to 4,096.

| shape | us a dispatch |
|---|---|
| plain | 0.70 |
| a `setComputePipelineState` between every dispatch | 0.70 |
| a 16-byte `setBytes` between every dispatch | 0.70 |
| `dispatchThreadgroupsWithIndirectBuffer`, one slot reused | 2.28 |
| the same, a distinct slot a dispatch - what the gate encodes | 2.25 |
| slotted, table in private storage | 2.22 |
| slotted, grid zeroed - what is left behind an abort | 1.85 |

Neither the pipeline switch nor the binding costs anything, so "one fewer
dispatch" is worth 0.70 us with the gate off. The indirect form adds 1.55 us
and nothing moves it: a distinct slot a dispatch reads the same as one slot
reused, so it is not a cache effect, and private storage is 0.03 us cheaper,
which is noise. A switched-off dispatch still costs 1.85 us, so the header's
claim that the dispatches behind an abort "still cost their issue" is now a
number.

Against a token's measured **2,666.6** gated dispatches (the zero-abort window;
a counter was added to the window report to get it), the gate's own tax is
2,666.6 x (2.25 - 0.70) = **4.13 ms a token**, 10% of a 39 ms GPU term. No
cheap mechanism has been found for it. A compute `MTLIndirectCommandBuffer`
is concurrent-dispatch only, so it cannot express the forty-layer chain.

## The rounding pass the producer can do itself: -586.5 dispatches, -4.7 ms

A call-site census (`DS4_METAL_V41_GATE_CENSUS=1`, two frames of return
address) says where a token's 2,666.6 dispatches come from. The largest single
entry is `ds4_gpu_dsv41_quantize` at **759.5 a token - 28% of all of them** -
and nineteen of them a layer. Nearly every matmul and every norm on the decode
path was followed by a dispatch that read the row back and rounded it to BF16.

The value that pass re-reads is the value the producer had in a register, and
BF16 rounding is idempotent, so rounding before the store is the same bits.
`helper_mv_reduce_and_write` is the one store every matvec goes through, so
Q8_0, F16 and F32 fall to one flag; the weighted RMS norm, the HC expand, the
shared SwiGLU and the MoE add take the same flag one at a time. The matvec
forms report whether the path they took could honour it, and a path that
cannot leaves the caller running the pass it always ran.

`ds4_gpu_rms_norm_plain_rows_tensor` was on the list and has nothing to fuse:
its only caller, `ds41_hc_mix`, has no rounding pass after it.

2,666.6 -> 2,280.1 -> **2,080.1** gated dispatches a token, all of it quantize
(759.5 -> 373.0). Six prompts up to 2,048 generated tokens byte-identical with
the gate on and with it off. Two eight-run ABBAs, aborts per window identical
in every run: steady wall **49.79 -> 45.10 ms, 20.09 -> 22.17 tok/s**, with no
overlap between the arms - the worst fused run is 45.70 against a best baseline
of 47.55. Encode alone is -0.54 ms with the two distributions disjoint.

**How much of the 2.25 us is actually recovered depends on the kernel.** The
386.5 matvec dispatches of the first batch realised 0.79 of a predicted 0.87 ms
(91%); adding the 200 tiny elementwise dispatches of the second batch took the
combined figure to 0.70 of a predicted 1.32 ms (53%). A small kernel's issue
overlaps the previous kernel's execution and the saving does not appear. The
4.13 ms above is an upper bound, and its realisable fraction runs from about a
half to nine tenths.

## The expert cache, replayed against seven policies, and closed

Replaying the route log the validator already writes - no new trace - with the
metric being **aborting layers, not expert misses**: the gate stops a segment
at the first layer whose selection is not all reachable and repairs every
missing expert of that layer in one call, so two misses in one layer are one
abort. Misses overstate what a policy buys.

| policy | 7,930 | 8,698 |
|---|---|---|
| current, as implemented | 4.91 | 3.82 |
| global LRU | 4.91 | 3.82 |
| TinyLFU admission | 4.91 | 3.82 |
| 2Q | 5.25 | 3.88 |
| per-layer LRU, equal shares | 6.21 | 5.16 |
| per-layer LRU, shares by working set | 5.29 | 4.03 |
| Belady | 3.12 | 3.12 |
| infinite | 3.12 | 3.12 |

The simulator predicts the machine twice: 4.91 against a measured 4.94, and
3.82 against a measured 4.03 once the headroom is lent.

**The current policy is LRU.** It evicts by lowest route hotness and breaks
ties by last use, but hotness is halved every sixteen tokens, so almost every
entry sits at zero and the tie-break decides. TinyLFU is identical for the
same reason: a candidate is incremented on the access that misses, the victim
is usually at zero, so it always admits.

**Per-layer allocation and admission control both make it worse.** The
suspicion that a global policy lets one layer's one-shot experts evict
another's hot ones is not supported: splitting the budget by layer costs 0.4 to
1.3 extra aborts a token however it is shared.

**Belady equals infinite at 7,930.** The working set fits; every miss beyond
the compulsory 3.12 is the policy's, not the capacity's. That is 1.79 aborts a
token, **2.0 to 2.3 ms** at the corrected steady price - and no online policy
tried recovers any of it.

Lending the headroom does move the count: 7,930 -> 8,698 entries, **4.94 ->
4.03 aborts a token**, deterministic, and byte-identical. It does not move the
time. Sixteen 1,000-token runs, eight an arm:

    base 43.6 44.2 44.3 44.3 44.9 50.0 50.7 52.4
    lend 43.1 43.1 43.2 43.6 44.1 45.1 53.1 59.3

Mean +0.05 ms, median -0.71, best four of each arm -0.83, against a prediction
of -0.99 to -1.16. The median and the best runs agree with the prediction and
the mean does not, because the two slowest runs of the whole session are in the
lending arm - which is the +7.12 GiB of locked footprint the mechanism's own
comment warned about, on a 128 GB machine.

So: the policy question closes on arithmetic - no online policy beats LRU, and
what an oracle leaves after lending is 0.91 aborts, about 1.0 ms. The capacity
question is real in misses and absent in time, and it makes the tail worse.
Neither is worth building on.

## Measuring on a machine that moves

Three things learned the hard way today, to add to the list above.

**The same window of identical work moves by a factor of two with machine
state.** Token 129 of this prompt has 14.00 command buffers, 0.00 aborts and
0.00 MiB loaded in every run ever recorded - the work is bit-identical - and
its commit-to-done was 35.08 ms on a quiet machine and 64.07 to 77.31 ms with
24 GB of swap in use. Check a known window against a known value before
believing any A/B, and record `vm_stat` around every arm.

**The routing is deterministic across runs.** Aborts per 64-token window come
out 27.95, 14.75, 0.00, 7.44, 10.84, 11.08 in every run of the same prompt.
That is worth asserting in the analysis rather than assuming: it makes a
window-by-window comparison exactly paired, and it catches a mixed-up arm.

**Use a covariate instead of discarding runs.** With the zero-abort window as a
per-run state proxy, `steady ~ state + arm` recovers the arm effect over
eleven runs without dropping any of them, and reports the state slope so the
reader can see how much of the spread was the machine.

## Two corrections to the section above, and what they open

**"Belady equals infinite, so the cache closes" does not follow.** Belady is an
oracle over future routes. What it showed is that *with the future known, at
the capacity already installed*, aborts fall 4.91 -> 3.12. That is not a closed
door; it is the evidence that prediction is the lever. What closed is reactive
replacement - LRU, TinyLFU, 2Q, per-layer allocation - and that is all that
should have been written.

Nor is 3.12 a floor of *stalls*. It is a count of demand misses: first uses,
which an infinite cache still has to fetch. Knowing the id early enough moves
the fetch off the critical path without removing it. So there are two ceilings,
not one:

    reactive:    4.91 - 3.12 = 1.79 aborts a token ~ 1.9-2.3 ms
    predictive:  hide the demand abort itself = 4.91 x 1.08-1.26 ~ 5.3-6.2 ms

And this is not the speculative decoding that closed earlier. MTP predicts a
future *token* and needed 81-88% acceptance to pay. Predicting the route
predicts expert control inside the current, correct token, and the exact router
still decides; a wrong guess falls back to the gate that already exists, so the
output cannot move. The two share a word and nothing else.

### What the route log says a predictor would have to do

Replaying the same log, the obvious predictor is already dead: take the
previous token's selection for the same layer.

- exact set match **0.3%** of (token, layer); mean expert overlap **33.6%**,
  two of six, between 14% and 49% depending on the layer
- and prefetching it does nothing at all - **zero background loads, aborts
  unchanged** - because an expert used last token is at the MRU end of the
  cache by construction. Predicting what is already resident prefetches
  nothing.

The reason is in what the misses are. At 7,930 entries, steady state:

    5.36 misses a token
      never seen before in this generation : 3.31  (62%)
      seen before and evicted              : 2.05  (38%)
        tokens since last use: p10 482, median 571, p90 811

Sixty-two per cent are not in the history at all, and the rest have a reuse
distance far past anything recency can hold - which is why capacity moves them
and policy does not. **So the thing to predict is not which experts are hot. It
is what layer L's router will choose, before layer L runs.**

There is room to do it: aborting layers are spread evenly, 1.2 per ten layers,
so **75% sit at layer 10 or later** - more than 30 ms of lead inside the token
for a predictor that resolves by layer 10.

The route log cannot answer whether that is predictable: it records the
router's outputs and nothing else. Settling it needs a trace of layer L's
selection against the same token's earlier hidden state, or a cheap surrogate
router. That is the next measurement, and if it does not predict, the line
closes there.

### The covariate was post-treatment, and the conservative number was wrong

The zero-abort window was used as a per-run proxy for machine state. It is not
independent of the arm: that window contains the same dispatches the BF16
fusion removes, so its cost falls with the treatment and the regression
attributes part of the effect to the covariate.

It shows in the numbers. Raw, pooled over sixteen runs with the arms disjoint,
the fusion is **-4.57 ms a token**. The covariate model reported -1.04. The
"conservative estimate" of -1.04 to -1.24 given for this change is biased
toward zero and is withdrawn; the raw comparison is the result.

The rule that produced it needs narrowing too. "Take out the term the change
cannot touch" is not general - a change can move GPU/CPU overlap and resource
contention, and repair-load is not guaranteed additive. **Keep raw wall as the
primary result always**, and use a term as a variance-reduction covariate only
where it has been confirmed additive, independent, and unaffected by the arm.

## Route prediction, measured and closed

The section above left one question open and named the measurement that would
settle it: can layer L's selection be predicted from the same token's earlier
hidden state? It can be, a little, and not nearly enough. Both ways of
spending a prediction - prefetch and replacement - are now measured, and both
are worse than doing nothing.

### The instrument

`DS4_METAL_V41_ROUTE_PREDICT=<path>` (in `ds4.c`, beside the gate trace, gate
off). At each layer S it runs layer T's own router - `ffn_gate_inp[T]` against
the norm S just produced, through the select kernel the decode path uses - for
T at offsets 0, 1, 2, 3, 4, 6, 8, 12, 16, 24 and 32 ahead, and writes the
predicted ids into a GPU buffer that is read once a token. **The surrogate is
the production router**, so there is nothing trained, nothing replicated
offline, and no way for the predicted selection to be produced by a rule other
than the one that decides the real selection.

Two checks before any number below is used.

**Offset 0 is the self-check.** A layer predicted from its own norm must
reproduce its own selection exactly, and it does: 11,240 of 11,240 pairs, 100%
of experts, zero extras. The probe's matmul, its bias, its select kernel and
its slot addressing are all therefore the decode path's.

**The probe does not perturb the graph.** The routes it records are identical
to the route log taken days earlier from a build without it - 4,520 of 4,520
(token, layer) selections over the first 113 tokens, after which the two
generations diverge and comparison stops meaning anything. That log is written
only inside the gated region, so the same check says a second thing: the abort
gate does not move the routing either, which is what lets a trace taken with
the gate off be used to size a mechanism that would live behind it.

561 decode tokens, one prompt. Scored on the second half only. The simulated
cache is still filling at the end of a run this short, so it reports 6.01
misses and 5.52 aborting layers a token against the 5.36 and 4.91 of the
1,162-token log; that biases the miss counts up and leaves the recalls alone.

### It predicts, and it predicts the wrong ones

| lead | recall | exact | recall of the experts that missed | layers whose whole missing set was named |
|---|---|---|---|---|
| 1 | 65.8% | 7.9% | 38.2% | 35.9% |
| 2 | 57.2% | 3.0% | 30.2% | 28.0% |
| 4 | 47.2% | 1.0% | 22.7% | 20.5% |
| 8 | 35.1% | 0.1% | 15.2% | 13.5% |
| 12 | 27.0% | 0.0% | 12.5% | 10.6% |
| 16 | 20.8% | 0.0% | 9.9% | 8.6% |
| 32 | 8.2% | 0.0% | 5.7% | 5.8% |

Two-thirds of a layer's selection is visible one layer early, and the signal is
gone by the time the lead is long enough to be useful. **And recall on the
experts that actually miss is always about half of overall recall**: the
predictor is right about the experts that were resident anyway and wrong about
exactly the ones worth fetching. That is the same fact the miss breakdown
already showed from the other side - 62% of misses are first uses in the
generation, and a first use is by construction the unusual selection.

### Prefetching it costs five to a hundred times what it saves

A predicted expert that the router did not choose is not free: if it is not
resident it is a wire, a read, and - at a full cache, where every add needs an
evict - the loss of an entry that was going to be used.

| lead | candidates | layers made abortable | aborts hidden a token | wasted loads a token | ratio |
|---|---|---|---|---|---|
| 1 | 6.0 | 35.9% | 1.93 | 10.66 | 0.18 |
| 1, union of 3 sources | 9.7 | 46.3% | 2.48 | 36.91 | 0.07 |
| 2 | 6.0 | 28.0% | 1.45 | 16.04 | 0.09 |
| 4 | 6.0 | 20.5% | 1.01 | 20.61 | 0.05 |
| 8 | 6.0 | 13.5% | 0.58 | 26.34 | 0.02 |
| 16 | 6.0 | 8.6% | 0.27 | 30.52 | 0.01 |

The baseline loads 6.01 experts a token. The cheapest useful arm here adds
10.66 more, and the ones that buy the most add thirty to forty-five.

The lead column makes it worse rather than better. A token is 45.10 ms over
forty layers, so **one layer of lead is 1.13 ms, and page wiring alone is about
1.7 ms an expert**: at lead 1, where the prediction is least bad, the prefetch
cannot finish before the layer needs it. The first lead that covers a fetch is
2, and there the arithmetic is 1.45 aborts hidden - 1.6 to 1.8 ms at the
corrected steady price - against 16.04 extra loads and 16.04 extra evictions.

### Using it for replacement instead buys nothing

Replacement is the other way to spend a prediction and it has no bandwidth
cost at all: touch the predicted entries that are already resident, so they
move to the MRU end and are not the next victim, and load nothing. This aims
squarely at the gap the policy replay left - an oracle's aborts against LRU's -
and the predictor is a claim to know that future.

| policy | miss/token | aborts/token |
|---|---|---|
| LRU, as shipped | 6.01 | 5.52 |
| + predicted, lead 1 | 5.97 | 5.50 |
| + predicted, leads 1-4 | 6.10 | 5.56 |
| + predicted, leads 1-16 | 6.23 | 5.64 |
| Belady | 5.57 | 5.15 |

0.02 aborts a token at best, and negative as soon as more than one lead is
protected. The reason is the reuse distance already measured: an evicted
expert was last used a median of 571 tokens ago, which is 22,840 layer
accesses, and protecting something one to sixteen layers ahead does not reach
anything at that range.

### And the transactional segment cannot commit

Candidate 2 needed a whole segment's routes predicted exactly, all of them from
the state at the segment's entry, or the shadow is thrown away:

    1 layer   7.893%
    2 layers  0.450%
    3 layers  0.010%

At the segment length the gate actually runs, a shadow would be discarded on
999 tokens in 1,000. There is no version of this that pays for its own
encoding, let alone the indirect tax it was meant to remove.

### What this closes, stated narrowly

What is measured and negative is **the unconditional predictor: take the
predicted top-6, prefetch all of it, at every layer** - and, separately,
**all-or-nothing segment prediction**. Both lose in wall terms at every lead
time, and the second cannot commit often enough to pay for its own encoding.

**What is not measured is a selective predictor.** The signal is real - 38.2%
of the experts that actually miss are named one layer early - and the loss
above is a precision problem, not a recall one: every prediction is acted on,
so the false positives are paid for in full. A confidence threshold on the
router's own margin, prefetching only where the prediction is strong, has not
been tried. It is left untried deliberately: **the whole prize at a lead that
can complete a fetch is 1.45 aborts, 1.6 to 1.8 ms**, so even a perfect filter
sits under the 2 ms bar this page uses to decide what to build. Record it as
untested, not as closed.

What survives is the framing, which was right: the exact router still decides
and a wrong guess falls back to the gate, so nothing here could have moved the
output. The idea was sound and the signal, at the lead times that matter, is
too weak to pay.

It also narrows the reading of Belady. The correction two sections up said the
gap was "the future, not the capacity". That is true and the future that closes
it is hundreds of tokens of route, not tens of layers: nothing inside the
current token carries it, which is what this trace settles.

### Rules this adds

16. **A predictor has to be scored on the events it is meant to prevent, not
    on its own output.** Overall recall was 65.8% and recall on the experts
    that actually missed was 38.2%, because the easy cases and the useful cases
    are disjoint. Reporting the first would have justified building the second.
17. **Price the false positives in the same units as the true ones.** Every arm
    above has a defensible recall and every one of them loses, because the cost
    was counted in loads and evictions rather than in percent.
18. **A lead time is only lead if it is longer than the thing it hides.** Lead 1
    is the best arm on every accuracy column and cannot complete a fetch: 1.13
    ms of layer against about 1.7 ms of page wiring.

## The gate's indirect tax, part one: the prefix that cannot abort

The gate sends every dispatch of a gated segment through an indirect argument
buffer so that the layer which aborts can zero the rest. `proto/dispatchcost.m`
prices that at 1.55 us a dispatch over a plain one. Not every dispatch needs
it.

**A command buffer has a prefix that is certain to run**, and the argument is
structural rather than statistical, which is what the byte comparison below
supports rather than establishes:

1. a segment is exactly one command buffer - `ds4_gpu_gate_segment_begin` is
   called once per buffer and `end_commands` commits and waits before the next;
2. the miss record is `memset` on the host inside `segment_begin`, after the
   previous buffer has completed, so no abort survives into this one;
3. the validate kernel is the only writer of that record, anywhere;
4. dispatches execute in encode order within a buffer.

So every dispatch encoded before the buffer's first validate runs, in every
execution, whatever any layer decides. Sending it indirect buys a switch that
cannot be thrown. What the byte-identity runs then check is that this reasoning
was implemented correctly, not that it is true.

The prefix is not small. A segment's first layer contributes its attention, its
router and its shared expert before its validate is reached; a continuation
resumed from a repaired layer contributes that layer's routed experts, its
finish, and the whole of the next layer up to *its* validate, because the
repaired layer's validate is not re-encoded. At two to three layers a segment
that is roughly one layer in three, and a token is seventeen to nineteen
buffers.

So: `g_gate_armed`, cleared at `ds4_gpu_gate_segment_begin` and set inside
`ds4_gpu_gate_encode_validate` *after* it has encoded its own dispatch, so the
first validate of a buffer is itself plain. `DS4_METAL_V41_GATE_DIRECT_PREFIX=0`
puts everything back.

**The one number that had to change with it** is the slot the validate starts
zeroing from. It was `slots_used() + 1`, which assumes the validate took a slot
itself. The first validate of a buffer does not, so it is now
`slots_used() + (the next gated dispatch will take a slot ? 1 : 0)`. Off by one
here leaves a live dispatch behind an abort - which is exactly what
`ds4_gpu_gate_slots_left_live()` reads back and counts, so the gate's existing
self-check is the check on this line.

### What it moves

Steady windows, six prompts, the two arms doing identical work (7.40 aborts a
token and 350.0 dispatches behind an abort in both):

| | direct prefix off | on |
|---|---|---|
| indirect dispatches a token | 2,479.6 | 1,543.5 |
| plain, ahead of the first validate | 0.0 | **936.2** |
| dispatches the gate failed to switch off | 0 | 0 |
| dispatches it could not gate | 0 | 0 |

**The population these numbers count is "dispatches the gate would send
indirect", not every dispatch a token issues.** It excludes what is encoded
before `segment_begin` (the embed, and any layer below the gate window), which
was always plain, and the two non-uniform dispatches the gate cannot express.
Within that population the arithmetic closes:

    2,479.6 eligible = 936.2 converted to plain + 1,543.5 left indirect

The same closure holds window by window, including while the cache is still
filling, where the counts are larger because an abort re-encodes its layer:
3,511.9 = 1,900.3 + 1,611.6, and 2,934.6 = 1,681.3 + 1,253.3. **Those are the
filling regime, a different scope from the 2,479.6 above, and must not be mixed
with it** - the steady figures are the ones a change is priced against.

**About 37% of the eligible population no longer goes through the indirect
buffer** - 936.2 a token on the six correctness prompts, 855.7 on the prompt
the timing campaign used, the difference being how many aborts each prompt has.
At 1.55 us the upper bound is **1.45 and 1.33 ms a token** respectively, and at
the 53-91% the BF16 fusion realised of its own bound, 0.77 to 1.32 ms.

### Byte identity

Six prompts, up to 2,048 generated tokens, `DS4_METAL_V41_GATE_DIRECT_PREFIX`
on against off, same binary: **all six byte-identical.**

    breakout d68de436  haiku 7a706776  json 412ef20f
    long     c7456ea2  proof be6e3525  quicksort c6453f19

### The time: -1.58 ms a token, and the interval contains zero

Twenty runs, five ABBA blocks of (on, off, off, on), one prompt of 1,400
generated tokens each, the same binary throughout (md5 30fa947f, checked at
both ends). The analysis was fixed in writing before any of it was read: raw
wall is the primary result, a run collapses to the median of its steady windows
(start >= 449) because a run's windows are one generation on one machine state
and not independent samples, the block is the unit of pairing, and no run is
dropped.

The work is identical across all twenty runs: 17.03 command buffers and 4.52
aborts in every copy of every shared window, zero dispatches the gate failed to
switch off, zero it could not gate. One window differs by 0.1 in
dispatches-behind-an-abort in one run and in nothing else, which is a rounded
mean and not a difference in work.

| block | on | off | difference |
|---|---|---|---|
| 1 | 51.56 | 54.29 | -2.73 |
| 2 | 55.41 | 59.19 | -3.78 |
| 3 | 56.80 | 56.17 | **+0.62** |
| 4 | 56.34 | 57.72 | -1.38 |
| 5 | 55.60 | 56.21 | -0.61 |

**Mean -1.58 ms a token, median -1.38, 95% CI [-3.73, +0.58], four blocks of
five favouring the direct prefix.**

Beside it, and not used to adjust it: `commit-to-done`, the GPU term the change
is aimed at, moves **-1.18 ms with all five blocks agreeing in sign**, and host
encode moves -0.05. That the saving sits in the GPU term and not in the host's
encoding is what the mechanism predicts - the cost removed is the command
processor fetching indirect arguments, not the host writing them.

**So the honest statement is a point estimate of 1.2 to 1.6 ms a token whose
interval contains zero.** The block differences have a standard deviation of
1.73 ms, so five blocks give a half-width of 2.15 and cannot separate an effect
of 1.6; at that spread it takes **eight blocks, thirty-two runs**. The machine
was in 21 GB of swap for the whole session and ran the 45.10 ms token at 55 to
57 ms, which is the regime rule 11 warns about.

The change stays: it is byte-identical, it strictly removes indirect dispatches,
and there is no mechanism by which it can cost time. But **-1.58 ms is a point
estimate, not a measured result**, and the page should not carry it as one until
a quiet machine or thirty-two runs says so.

### Rules this adds

19. **Check that a prompt reaches the steady region before using it for an A/B.**
    The first timing campaign used the breakout prompt, which stops on its own at
    about 512 generated tokens and leaves exactly one window past the cache
    filling. Fifteen steady windows a run came from changing the prompt, not the
    statistics.
20. **State the population a dispatch count belongs to.** "Gated dispatches a
    token" is 2,359 in the steady region of one prompt, 2,480 in another, and
    3,512 while the cache fills, because an abort re-encodes its layer. They are
    the same measurement of different things and dividing one by another is how
    a 37% becomes whatever is wanted.

## Stage two: the live/zeroed census, and why it does not choose

`DS4_METAL_V41_GATE_CENSUS` now counts, per call site, how many of its
dispatches ran and how many the abort switched off. Every gated dispatch
records the slot it took, each validate records the slot it was told to start
zeroing from *as it was told it* rather than re-derived, and the join happens
once the buffer has completed and the aborting layer is known.

It was built to price the left half of

    live x 1.55 us  -  zeroed x (kernel time + 0.70 - 1.85) us

and what it says is that the left half is a constant. Over the 54 sites of a
steady window (tokens 641-704, 5.61 aborts a token, 1,502.6 indirect dispatches
a token):

| | live |
|---|---|
| lowest site | 76.8% |
| highest site | 89.1% |
| mean | 82.2% |

**Twelve points of spread across every call site in the token.** An abort cuts
at a layer boundary and every site appears in every layer, so they are all cut
at the same rate. There is no site that is systematically safer to send plain
than another.

So the expected value has one site-dependent term left and the decision
collapses to a single threshold:

    0.822 x 1.55 = 0.178 x (k - 1.15)   ->   k = 8.29 us

**A site is worth sending plain if its kernel runs in under about 8 us.** Above
that, the wasted executions behind an abort cost more than the indirect
arguments saved.

### What is left to settle, and why the census cannot

**Kernel time.** Metal gives no per-dispatch timing, so the only recorded proxy
is the grid, which the census already keeps:

| threadgroups a dispatch | sites | dispatches a token |
|---|---|---|
| 1 | 19 | 529.4 |
| 2 to 32 | 19 | 447.9 |
| 33 to 256 | 6 | 116.5 |
| over 256 | 10 | 408.8 |

The 529.4 from single-threadgroup sites cannot be worth 8 us, which bounds that
group at 529.4 x 1.55 = **0.82 ms a token**; the 2-to-32 group adds another
0.69 ms but will contain kernels over the threshold.

**Safety, which is per call site and has to be read rather than measured.** A
dispatch may be sent plain only if, run after an abort, it cannot corrupt
anything the continuation will not rewrite: it must not advance `previous_kv`
or `previous_score`, must not write KV, Engram, the residual carry, the route
log or an accounting counter, must not index from a stale id, and must have its
output regenerated by the continuation. That is a per-site reading of the code,
and the numbers above are before it, not after.

**So stage two ends with a threshold and a candidate pool, not a change.** The
census earned its place by producing the 8.29 us figure; it cannot rank the
sites, because on this metric they do not differ.

### And the candidate pool is empty

Symbolising the census against the binary's symbol table (`nm -n`, the census
records unslid addresses) gives the sub-threshold pool by name - the nineteen
sites that launch a single threadgroup, 529.4 dispatches a token - and every
one of them writes state a continuation reads without recomputing it.

Three facts from the code, which together are the reason:

1. `DS41_SCRATCH` allocates **one** set of tensors, not one a layer: a single
   `norm`, a single `selected`, a single `route_weights`.
2. A continuation resumes from the failed layer's **routed stage**. It does not
   re-run that layer's `ds41_graph_before_moe`, its `ds41_moe_route_row` or its
   validate - that is what `il == start && resume_from_moe` skips.
3. `ds41_moe_experts_row`, which is what the continuation runs first, reads
   `g->selected`, `g->route_weights` and `g->norm`.

So if a later layer's router or norm were left plain and ran after the abort,
it would overwrite, in the shared scratch, exactly what the continuation is
about to read. And the census says the cheap dispatches *are* the routers and
the norms:

| a token | site | what a continuation reads that it would overwrite |
|---|---|---|
| 112.2 | `rms_norm_weight_rows_round` <- `ds41_norm` | `g->norm` |
| 192.0 | the seven inside `ds4_gpu_encode_router_select` | `g->selected`, `g->route_weights` |
| 109.6 | `rms_norm_plain_rows` / `hc_split_sinkhorn` <- `ds41_hc_mix` | the HC mix behind after_attn and ffn_split |
| 54.8 | `dsv41_rope_stride`, `encode_cpy_f32_f16_1d` | the KV ring |
| 27.4 | `gate_encode_validate` | the abort record itself |
| 33.6 | indexer top-k, candidates, top-k mask | the indexer selection and candidate mask |

**529.4 accounted for, 0.0 left as a candidate.** The other side of the
threshold is the routed expert kernels themselves, at 640 and 1,728
threadgroups - and those are the dispatches that would read a missing expert's
address, which is the gate's whole reason for existing.

**The intersection of "under 8 us" and "safe" is empty, and it is empty
structurally.** It is not a classification that needs to be done more
carefully: as long as the scratch is shared between layers and a continuation
resumes part-way into one, the cheap dispatches are exactly the ones whose
output the continuation depends on.

So the indirect tax gives up what stage one took - the prefix that cannot abort
- and nothing further. Making more of it plain would need per-layer scratch for
`norm`, `selected` and `route_weights`, which costs allocation and touches the
graph everywhere, to chase a tax whose remaining realisable part is now
unknown and bounded above by 1,500 x 1.55 us = 2.3 ms a token.
