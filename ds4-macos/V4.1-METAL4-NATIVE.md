This is the goal and its acceptance list. `0e4eac7`
(`ds4-v41-metal4-single-host-exact-production`) is the fastest correct Metal 4
**submission** version: V4.1 commands go to a Metal 4 queue, but the engine
still encodes through the Metal 3 shape. That version is the performance
reference here. It is not the finished state.

## Acceptance list

1. V4.1 creates no Metal 3 queue, including at engine init.
2. The `g_batch_cb` disguise is gone: the engine's batch identity is no longer
   a Metal 4 object cast to `id<MTLCommandBuffer>`.
3. The `DS4Encoder` compatibility shim is off the V4.1 path.
4. V4.1 has a first-class Metal 4 command context.
5. The in-flight context owns its allocator, command buffer(s), argument
   table(s), constant scratch, residency set and feedback.
6. There is no mutable global argument table.
7. Ops form an explicit graph. Each op carries the buffer ranges it reads and
   writes, and the generation (version) of each range.
8. Barriers are generated from that graph, not from the order of legacy calls.
9. The structure supports encoding command buffers in parallel and submitting
   them with `commit:count:`.
10. The resident-layer service, the full expert address table and the encoder
    timeline are each either ported to Metal 4 or formally removed as V4.1
    features. None of them is silently disabled, silently falls back, or is
    refused at run time while the work is called complete.
11. Every single-host V4.1 path goes through the Metal 4 context: prefill,
    decode, native session batch, vision, the verify executor, disk KV,
    engine reopen, and failure paths.
12. Reach counts are all 0: Metal 3 command buffers, queues, encoders, events,
    blits and waits, and the shim.
13. The output matches the baseline exactly: token IDs, output bytes, every
    logit, and the KV and carry state.
14. That match reproduces at 2048 tokens, over several inputs, several
    sessions, and consecutive requests.
15. Sustained wall time does not regress against `0e4eac7`.

The baseline for item 13 is `ds4-v41-frozen-exact-production` (`c526a3b`,
Metal 3) with the configuration in `bench/sustained.sh`, together with
upstream main. Constraints carried over from the migration brief:

- use real weights and the real server path;
- add no new environment variables or ad-hoc flags;
- record revision, dirty state and binary hash for every run;
- push nothing until all fifteen items pass; then only the verified, tagged
  state, to the fork.

### The cache size changed the output, in the baseline too

Until `13c14ca`, a streaming prefill append of 256-1023 rows ran token-major
only when the configured expert cache held at least half the experts (7680 of
15360), and as one layer-major sweep below that. The two paths round
differently. The long prompt's 699-row tail after its first 4096-row chunk
therefore gave `e197891559449b7b` at the frozen baseline's production cache
(9648) and `6d29be99270ceecf` at 4096-7041 - in the clean baseline as much as
in the candidate, whose 80 GiB budget always kept it below the threshold.
The rule is now the baseline's production one at every size, and the tail
reports its steps: 699 of 699 run token-major (`6749f95`). That costs a long
prompt's time to first token against a layer-major tail; making that tail
exact and batched is the next piece of work, not part of this list.

Source: the inventory of the V4.1 call closure in `ds4_metal.m`.

- **Wrappers.**
  - About 235 public `ds4_gpu_*` functions are reached from V4.1.
  - About 110 static encode helpers.
  - About 150-200 distinct pipelines.
  - About 664 `setBuffer:` sites in the closure; 1,325 in the whole file.
  - Every wrapper uses the Metal 3 shape:
    `ds4_gpu_command_buffer(&owned)` → `ds4_gpu_compute_encoder(cb)` →
    `[enc setBuffer:…]` → `ds4_gpu_finish_command_buffer`.
- **Metal 4 today.**
  - `DS4MTL4Encoder` answers those selectors (the shim).
  - `g_batch_cb` holds a `DS4MTL4Buffer` cast to a command buffer (the
    disguise).
  - One global `g_mtl4_table` serves every dispatch.
  - Barriers follow call order: after every dispatch in a serial section, and
    at every section end.
- **Buffer ranges.**
  - About 36% of bindings are tensors, where the byte range is known.
  - About 33% are buffers passed down by callers.
  - About 18% are engine globals (`g_flash_attn_*`, `g_moe_*`, `g_parallel_*`,
    `g_kv_task.*`, gate buffers).
  - About 8% are model weight views.
  - Every tensor allocation is its own `MTLBuffer`, so "from the binding's
    offset to the end of its buffer" is a sound range for any binding.
- **Engine init.**
  - `ds4_gpu_init` creates the Metal 3 `g_queue` (`ds4_metal.m:7594`).
  - For V4.1 it is first reached from `ds41_memory_admit` →

  - The model family is known from `config_validate_model` onwards, before
    that call, so creating the queue can be deferred.
- **Features that only exist on Metal 3.**
  - Resident-layer service, about 450 lines: event wait, service thread, blit.
  - Full expert address table, about 400 lines: separate command buffer,
    blit into private scratch, `waitUntilCompleted`, queue residency set.
  - Encoder timeline, about 400 lines: counter sample buffers, completion
    handlers.

## Design

### Command context (items 2-6, 11)

`ds4_m4_ctx` is one in-flight submission. It owns:

- an allocator and its command buffers;
- one argument table per encoding thread;
- constant scratch;
- a residency set;
- its commit stamp and feedback slot.

A small pool of contexts replaces `g_mtl4_pool`, `g_mtl4_cur`, `g_mtl4_enc`
and `g_mtl4_table`. The engine's batch identity becomes a typed `ds4_cmd *`
handle:

- On V4.1 it names a context. Expert-cache bookkeeping keys on the context's
  stamp and sequence number, not on an object pointer.
- On other model families it wraps a Metal 3 command buffer.
- `g_batch_cb` is Metal 3 only, and V4.1 never sets it.

### Op API (items 3, 7)

Wrappers encode through a C op API instead of Objective-C messages to an
encoder:

- `ds4_enc_begin(cmd)`
- `ds4_enc_pso`
- `ds4_enc_buf(idx, buffer, offset[, bytes])`, and `ds4_enc_tensor(idx, t)`
  for an exact range
- `ds4_enc_bytes`
- `ds4_enc_tgmem`
- `ds4_enc_use(resource, usage)`
- `ds4_enc_dispatch`, `ds4_enc_dispatch_threads`
- `ds4_enc_copy`
- `ds4_enc_end`

The Metal 3 implementation calls `MTLComputeCommandEncoder` directly. On
V4.1, each call records a node into the context's graph:

- the pipeline, bindings, constants and grid;
- read and write ranges;
- the generation of each range it touches.

Read or write access comes from each pipeline's binding reflection, captured
when the pipeline is built (`MTLPipelineOptionBindingInfo`). A binding with
unknown access counts as read-write. Ranges are:

| Operand | Range |
|---|---|
| Tensor | its bytes |
| Any other binding | offset to the end of its buffer |
| Copy | what it copies |
| Gated dispatch | reads its 12-byte grid slot |
| `ds4_enc_use` | the whole resource, read or written as its usage says |

Converting the wrappers is mechanical: message sends become calls, and
`id<DS4Encoder>` / `id<MTLCommandBuffer>` parameters become `ds4_enc *` /
`ds4_cmd *`. It is applied to the whole file, so `DS4Encoder` and
`DS4MTL4Encoder` are deleted rather than bypassed.

### Barriers from the graph (item 8)

When a context is submitted, its nodes are encoded in order. A barrier goes
in only before a node whose ranges conflict with something since the last
barrier: read after write, write after read, or write after write. The
engine's concurrent-section calls and `memoryBarrier` calls are no longer
barriers on V4.1.

Hidden accesses are the risk:

- Kernels read expert weights through raw addresses in tables. The slabs they
  read are written only by the host loader, which is ordered by commit, not
  by barriers.
- Every such read that the engine declares with `useResource` becomes a read
  node.

Item 13's byte comparison covers every conflict key.

### Parallel encoding and `commit:count:` (item 9)

Nodes are recorded first and encoded at submission, so one context's graph
can be split at barrier points:

- the parts are encoded on worker threads, each part into its own command
  buffer with its own argument table;
- all of them are submitted with a single `commit:count:`.

The queue-stage barrier at the start of each later buffer orders it after the
one before. Encode-ahead and commit-ahead stay: they are contexts in flight.

### Metal 3-only features (item 10)

Each gets its own decision:

- **Full expert address table.** Port it: the prewire copy runs in a context,
  and its residency set joins the Metal 4 queue.
- **Resident-layer service.** Port it or remove it. Its host thread and event
  wait map to a Metal 4 `waitForEvent` on the queue, so the decision rests on
  its cost against its use.
- **Encoder timeline.** Port it or remove it. The Metal 4 form is timestamp
  writes into an `MTL4CounterHeap`.

Whichever way each goes, the decision is recorded with its reason in this
file and in the code. After that, V4.1 has no refusal branch left for any of
the three.

### Init (item 1)

- `ds4_gpu_init` creates the device, the library and the probes that do not
  need a queue.
- The Metal 3 queue is created the first time Metal 3 is selected or used.
- `ds4_gpu_use_metal4()` runs before anything could reach that point.
- A counter reports how many Metal 3 queues were created, and V4.1 must show
  0.

## The command-graph measurement, redone

The first replay (`1adbfa9`) is withdrawn; see `V4.1-TUNING.md`. The redo:

- **Starting state.** Every buffer the token writes on the GPU is copied
  before the token and restored before each arm.
- **Reference.** What the live token left is the reference. R1 must reproduce
  it, and R3 and R4 are compared with R1, all bytes.
- **Boundaries.** Replay uses production's command buffers, queue barriers
  and visibility.
- **Dependency keys.** Keys are byte ranges.
- **Order.** Arm order rotates each round.
- **R2** is labelled an invalid control.
- **Aborted tokens** are measured live as their own population and not
  replayed. Between segments the host loads an expert, and a replay would find
  it already present.

Whatever this finds bears only on today's dispatches. It does not rule out
fusion, tile-level producer/consumer, or persistent kernels.
